Front MatterAbout this document

This is the integration guide for the Woohoo V2 backend. It documents what you send, what you get back, and what the service does in between. It is a companion to the architecture document in docs/architecture/, which explains why the design is shaped this way; section references like §19 point there.

Everything here is verified against the running build

Every JSON example in this document was produced by executing the request against the service, not written by hand. The tool tables were generated from the TypeScript definitions in packages/contracts/src/tools.ts. If the code and this document disagree, the code is right and this document is stale — regenerate it.

Who this is for

  • Android / device engineers — Parts II and III. The WebSocket is your path.
  • Anyone testing or scripting — Part IV. The HTTP endpoint is curl-able.
  • Anyone extending the agent — Parts V and VI. The tool surface and the capability model.
  • UI engineers — read Part VIII first. The staff/admin API does not exist yet, and that section says exactly what is missing.

Part IOrientation

1. The two surfaces, and which to use

The service exposes exactly two network surfaces, both on one port (8443 by default). Hotel networks pass 443 and little else, so asking for a second port means asking for a firewall change nobody will make (§22).

SurfaceUse it forWhyDo not use it for
WebSocket
ws://host:8443/		 The production device path. The Woohoo hub in the guest room. A TLS handshake per turn costs 200–400 ms against a 1,100 ms p50 budget. Only a persistent connection can carry server-initiated pushes — screen updates and late BMS confirmations that arrive after the assistant has already spoken. Scripting and one-off tests. It is more setup than you need.
HTTP
POST /v1/turn		 Testing, curl, CI checks, a first integration spike, any non-voice caller. Request/response is trivial to call from anything. It runs the identical orchestrator path, so behaviour cannot drift between the two. The shipping device. You lose the filled pause, barge-in and server push.
If you only read one thing

Both surfaces take a device ID and a transcript. Neither takes a room number, a property ID or a tenant. Those are derived server-side from the device identity and cannot be supplied by the caller — that is the single most important property of this API and the reason a compromised or confused client cannot reach another guest's room.

2. Running the service

npm install
npm run gateway          # WebSocket + HTTP on :8443

# no API key, no Docker, no database required —
# in-memory stores and a deterministic mock LLM by default.
# set GOOGLE_API_KEY to switch to real Gemini.

Two other entry points are useful while integrating:

npm run turn -- "turn on the lights"     # one-shot, prints lane / verdicts / trace
npm run turn                             # interactive REPL, session persists
npm run turn -- --trace "it's freezing"  # full per-turn span tree

3. What happens during a turn

Between your request and the reply, this runs. Understanding it explains most of the fields you get back.

  your request  { deviceId, transcript }
        │
        ▼
  ① IDENTITY      device_id ──► { tenant, property, room } + capability manifest
                  Cached. This is the ONLY place scope is created, and it comes from the
                  device record — never from your payload.
        │
        ▼
  ② REDACTION     card numbers blocked outright; emails, IDs and names masked before the
                  transcript reaches the model or the audit store.
        │
        ▼
  ③ PRE-FETCH     room state · open tickets · stay context · preferences — all in parallel.
                  This removes a whole tool round-trip from most turns.
        │
        ▼
  ④ TOOL SURFACE  generated from THIS room's capability manifest. A room without curtains
                  has no curtain tool, so the agent cannot propose one.
        │
        ▼
  ⑤ ROUTER        fast · agentic · clarify · confirm      (see §14)
        │
        ▼
  ⑥ AGENT         Gemini (or the mock) proposes zero or more tool calls.
        │
        ▼
  ── for EVERY proposed call ──────────────────────────────────────────────
  ⑦ VALIDATE      against the tool's schema; unknown fields are rejected, not ignored
  ⑧ SCOPE         model-supplied room/property/tenant fields are STRIPPED, real scope injected
  ⑨ PRICE         monetary effect computed by the platform, never taken from the model
  ⑩ POLICY        the PDP returns ALLOW / CONFIRM / DENY / ESCALATE      (see §16)
  ⑪ AUDIT         the verdict is written BEFORE execution, so a crash still leaves evidence
  ⑫ EXECUTE       MCP gateway ─► domain module ─► automation adapter ─► the room
  ⑬ VERIFY        read the state back. "Done" is only said when it is observed done.
  ─────────────────────────────────────────────────────────────────────────
        │
        ▼
  ⑭ COMPOSE       templated where the outcome fits a known shape; model text otherwise
  ⑮ GUARD         no other-room references, no prompt leakage, length capped
  ⑯ SEAL          immutable turn record + turn.completed event
        │
        ▼
  reply  { speech, screen?, lane, calls[], ... }
Why step ⑩ matters to you as an integrator

The model proposes; the platform disposes. A tool call appearing in the calls array does not mean it ran — check verdict and ok. A DENY is a normal, expected outcome, not an error, and the ruleId tells you which rule fired.

Part IIWebSocket Protocol

4. Connecting

PropertyValue
URLws://host:8443/ — wss:// in any deployed environment
SubprotocolNone
FramingText frames carry JSON control messages. Binary frames are reserved for Opus audio and are not yet handled.
EncodingUTF-8 JSON, one message per frame
LifetimeOne persistent connection per device, kept warm. Do not open a connection per turn.
Auth (today)deviceId in the hello frame
Auth (production)mTLS client certificate; the device ID comes from the certificate subject and the hello field is ignored. See §10.

The first frame you send must be hello. Any other frame before it is rejected with NOT_AUTHENTICATED.

5. Client → server messages

send hello

Establishes identity. Must be first. The server resolves the device to its property, room and capability manifest, and replies ready or closes the socket.

{ "type": "hello",
  "deviceId": "d_412a",           // required
  "firmware": "2.4.1",            // optional, for fleet telemetry
  "certificateSerial": "cert_..." // optional today; authoritative under mTLS
}
send turn

One guest utterance, already transcribed. This is the main message.

{ "type": "turn",
  "transcript": "close the curtains and make it warmer",
  "asrConfidence": 0.94          // 0–1, optional, defaults to 0.95
}

asrConfidence is not decorative: below 0.60 the router sends the turn to the clarify lane and asks the guest to repeat rather than guessing at an action. Below 0.85 the deterministic fast path is disabled. Pass a real value from your ASR engine.

send barge_in

The guest started speaking while the assistant was talking. Accepted and reserved; playback control is currently the device's responsibility.

{ "type": "barge_in" }
send health

Device telemetry. Accepted on this channel for the single-process dev stack; in production it moves to a separate MQTT channel so telemetry backpressure can never reach the voice path.

{ "type": "health", "rssi": -58, "wakeFalseAccepts": 3 }

A rising wakeFalseAccepts count usually means the device is next to a television.

send ping

Application-level liveness check. Answered with pong. Independent of the WebSocket protocol-level ping the server sends every 30 seconds.

{ "type": "ping" }

6. Server → client messages

receive ready

Identity accepted. Everything here is derived from the device record.

{ "type": "ready",
  "property": "Demo Hotel Whitefield",
  "room": "511",
  "assistantName": "Voice Genie",
  "phrasePackVersion": "mock-voice-en-in@en-IN"
}

Use assistantName for on-screen branding and phrasePackVersion to decide whether your cached audio phrase pack needs refreshing.

receive ack

Arrives before the answer. Play this immediately from your cached phrase pack — it is the filled pause that keeps perceived latency near 600 ms even when the reasoning path takes longer.

{ "type": "ack", "filledPause": "Let me sort that—" }

The phrase rotates through six variants per language. A device that says the same three words every time sounds broken within a day.

receive speak

The spoken reply. Synthesise and play. Always under about 45 words by design.

{ "type": "speak",
  "text": "Curtains closed. I've set it to 22.5 degrees.",
  "turnId": "turn_ms6dstty0"
}
receive screen

Optional. Text for the device display, sent when the visual channel carries something the audio does not — an order total, an emergency number, evacuation guidance.

{ "type": "screen", "text": "Emergency: 112\nHotel team alerted" }
Accessibility

Render this. Voice must never be the only path: guests who are deaf, hard of hearing or non-verbal need every function reachable on screen, and in an emergency the screen works when speech does not.

receive error
{ "type": "error", "code": "RATE_LIMITED", "detail": "Too many requests from this device..." }
codeMeaningWhat the device should do
NOT_AUTHENTICATEDA frame arrived before helloSend hello, then retry
UNKNOWN_DEVICEDevice unknown, revoked, or its room binding is brokenSocket is closed. Do not retry in a loop — surface a provisioning error
RATE_LIMITEDMore than 30 turns from this device in an hourBack off; tell the guest to try shortly
BAD_FRAMEFrame was not valid JSONFix the client

7. A complete session

Captured from a live run against d_511a (room 511, a Suite). Nothing is edited.

--> {"type":"hello","deviceId":"d_511a","firmware":"2.4.1"}
<-- {"type":"ready","property":"Demo Hotel Whitefield","room":"511",
     "assistantName":"Voice Genie","phrasePackVersion":"mock-voice-en-in@en-IN"}

// compound request: two intents, one utterance
--> {"type":"turn","transcript":"close the curtains and make it warmer","asrConfidence":0.94}
<-- {"type":"ack","filledPause":"Let me sort that—"}
<-- {"type":"speak","text":"Curtains closed. I've set it to 22.5 degrees.","turnId":"turn_ms6dstty0"}

// chargeable action: the total is stated and consent is asked for — nothing is ordered yet
--> {"type":"turn","transcript":"I'd like a club sandwich","asrConfidence":0.96}
<-- {"type":"ack","filledPause":"One second—"}
<-- {"type":"speak","text":"I have 1 item ready to order. That's 850 INR, charged to your room.
                            Shall I place it?","turnId":"turn_ms6dsugd1"}
<-- {"type":"screen","text":"I have 1 item ready to order. That's 850 INR, charged to your room."}

// the confirming turn executes the FROZEN action, byte for byte
--> {"type":"turn","transcript":"yes","asrConfidence":0.99}
<-- {"type":"ack","filledPause":"On it—"}
<-- {"type":"speak","text":"Ordered — about 30 minutes. 850 INR has gone to your room bill."}

Note the shape of the exchange: one turn in, one ack plus one speak out, with an optional screen. There is no correlation ID on the request — the connection is per-device and turns are serialised, so the turnId on the response is the identifier you log against.

8. Reconnection and liveness

  • The server sends a protocol-level ping every 30 s and terminates a connection that misses two. Your client must answer pongs; most WebSocket libraries do this automatically.
  • On disconnect, reconnect with exponential backoff and full jitter, 1 s → 60 s cap. The jitter is mandatory. Without it a property-wide network blip becomes a synchronised reconnect storm from 300 devices, and you will have caused your own outage.
  • After reconnecting you must send hello again. Session state (conversation history, a pending confirmation) survives on the server for 30 minutes keyed on the room, so a brief drop mid-conversation does not lose context.
  • A pending T3 confirmation expires after 90 seconds regardless of connection state. If the guest reconnects after that and says "yes", they are told the confirmation expired and nothing is charged.

Part IIIDevice Integration

9. What the device owns

The service deliberately owns as little of the audio path as possible, and the device owns as little of the decision path as possible. This split is the point.

ResponsibilityOwnerNotes
Wake word detectionDeviceMust be local. Audio never leaves the room until the wake phrase fires; a 500 ms pre-roll buffer stops the first syllable being clipped, and the buffer is discarded otherwise.
Acoustic echo cancellationDeviceMust run before the signal leaves the mic path or barge-in is impossible.
Voice activity detection & endpointingDeviceSignal end-of-turn explicitly rather than letting the cloud wait out a silence timer. Worth 200–400 ms per turn.
Speech-to-textCloud (not yet built)Today the device sends text. When the ASR adapter lands, the device will stream Opus and the gateway will transcribe.
Intent, decision, authorisationServiceAll of it. The device never decides what an utterance means.
Text-to-speechCloud + device cacheCommon phrases (acknowledgements, confirmations) should be pre-synthesised into a device-side phrase pack.
Screen renderingDeviceServer-driven content; the device renders, never decides.
Offline fallbackDevice + edge~25-phrase local grammar reaching the on-prem edge gateway over the LAN when the WAN is down.

10. Identity and scope

This is the security model in one page, and it is worth understanding before you write client code.

  device certificate  ──►  device_id  ──►  catalog.resolveDevice()
                                                │
                                                ▼
                        ┌───────────────────────────────────────────┐
                        │  scope = { tenantId, propertyId,          │
                        │            roomId, deviceId }             │
                        │  + capability manifest for THIS room      │
                        └───────────────────────────────────────────┘
                                                │
       every tool call is executed under this scope, injected server-side.
       Scope fields present in model output are STRIPPED, never validated.
Do not send a room identifier. There is nowhere to put one.

No message in this API accepts a room, property or tenant. No tool schema has a room_id field. This is deliberate: validating a caller-supplied room would mean the field exists, which means it can be populated, which means somebody eventually trusts it for a staff feature. Removing the field removes the class of bug.

The practical consequence for you: a device is bound to exactly one room. If a device is physically moved during a refurbishment, the binding must be updated in the catalogue or it will confidently control the previous room. The service exposes verifyBinding() for periodic reconciliation against the automation system, and this is a real operational hazard rather than a theoretical one.

10.1 Today versus production

AspectToday (this build)Production target
Device identitydeviceId string in helloPer-device X.509 certificate, private key held in the Android Keystore / StrongBox and non-exportable
Transportws://wss:// with mTLS, TLS 1.3, certificate pinning plus a documented rotation path
Credentials on deviceNoneNone — and this must stay true. A stolen device should yield only a revocable, room-scoped certificate
Revocationrevoked flag on the device recordCRL / OCSP plus immediate connection termination
Migrating the existing Android app

The current com.sb.woohoo build ships cloud credentials — a Google service-account path and AWS Polly keys — and calls Google STT directly over gRPC. The highest-priority change is removing them: today a device stolen from a guest room is a credential compromise, and the credential is not scoped to that room. Replacing the direct gRPC call with this WebSocket removes the credentials and lets you change ASR vendor, model and phrase hints without shipping firmware.

Part VResponse Semantics

14. Lanes

Every turn takes exactly one lane. The lane explains the latency and the behaviour.

LaneTypicalWhenWhat it means for you
fast~20–40 msHigh-confidence match against a curated grammar, all slots filled, single action, tier ≤ T2No LLM was called at all. Target is 55–65% of real traffic.
agentic~40–900 ms (mock)Everything else: compound requests, free text, relative changes needing state, questionsFull reasoning over the tool surface. With real Gemini expect ~1.9 s, masked by the filled pause.
clarify~1 msASR confidence < 0.60, or an ambiguous referent with no session contextA question was asked, no action taken. calls is empty.
confirm~1 msThe previous turn left a frozen chargeable action and this turn is yes or noNo model involved. The frozen action executes verbatim or is discarded.
degraded—The service is at degradation level 2 or higherReduced scope. The reply states what still works rather than what is broken.

14.1 Degradation levels

LevelTriggerGuest experience
0NormalFull capability
1LLM slow (p95 > 2.5 s)Unchanged — thinking budget capped, fast lane widened
2LLM errors > 10%Fast lane only; the reply names what still works. The route to a human stays open.
3ASR unavailableScreen UI takes over
4WAN downOn-device grammar → edge gateway → room systems. Lights, climate and DND still work.
5Edge unreachable tooHonest failure message pointing at the room phone

15. Risk tiers

Every tool carries a tier. The tier determines what the platform requires before the action reaches the world, and it appears on every entry in calls[].

TierCharacterRequirementExamples
T0Read-onlyScope check. Auto-execute.room.get_state, stay.get_info, fnb.get_menu
T1Reversible physicalScope + capability + bounds. Auto-execute, confirm verbally after.lighting.set, climate.set_temperature, curtains.set, dnd.set
T2Involves a humanScope + duplicate + rate limit. The reply must state exactly what was committed.service.create_request, stay.set_wakeup_call, staff.connect
T3MoneyMandatory spoken confirmation in a separate turn, within 90 s, plus spend caps.fnb.place_order
T4Safety-criticalNever executed by the agent. It may only raise; a human acts.staff.escalate_urgent
T5ProhibitedNo tool exists. Cannot be proposed.Door locks, safes, remote microphone, any cross-room or bulk action, card handling
There is no door-lock tool, at any tier

Guests will ask. A voice interface has no reliable speaker authentication and the room is accessible to anyone physically present, so the failure mode is a stranger entering an occupied guest room. No confirmation flow makes that acceptable, because the attacker and the guest are indistinguishable to the device. If it must ever exist it needs a second factor that is not voice — and it should be that authenticated app, not the voice device, that performs the action.

17. The confirmation protocol

The only two-turn flow in the API, and the one most worth implementing carefully.

 TURN N                                          TURN N+1
 ────────────────────────────────────────────    ────────────────────────────────────────────
 guest: "I'd like a club sandwich"               guest: "yes"
                                                 lane = "confirm"  (no model involved)
 → fnb.get_menu          ALLOW                   → validates the single-use token
 → fnb.place_order       CONFIRM                 → executes the STORED action verbatim
                                                    (NOT re-derived from this utterance —
 platform freezes, server-side:                      which is what makes injection useless)
   { token, tool, args, total, expires: 90s }    → marks the token consumed

 speech: "I have 1 item ready to order.          speech: "Ordered — about 30 minutes.
          That's 850 INR, charged to your                 850 INR has gone to your room bill."
          room. Shall I place it?"
 awaitingConfirmation: true                      awaitingConfirmation: false

                                                 "no" / timeout / anything ambiguous
                                                 → token discarded, nothing executed,
                                                   nothing charged, audit records it
The property that matters

The action executed on confirmation is the action that was authorised, byte for byte. The model does not get to reinterpret it. A guest saying "yes" can only ever confirm the frozen pending action or nothing at all — so an injected instruction in the confirming turn cannot substitute a different order.

Client requirements: treat awaitingConfirmation: true as a modal state, always render the screen text carrying the total, and let the guest cancel. Do not auto-confirm, ever.

Part VIMCP & the Tool Plane

18. What MCP means here

MCP — the Model Context Protocol — is how capabilities are exposed to a model. In Woohoo it is an internal plane. It is not a public API, and you do not call it directly: you send a transcript, and the agent decides which tools to propose.

Understanding it still matters to an integrator, because the calls[] array in every response is the tool plane's output, and because the tool surface is what determines what the assistant can and cannot do in a given room.

  AGENT ──── one connection ────► MCP GATEWAY ──┬─► property catalog
  (proposes only)                               ├─► device state ──► automation adapter ──► BMS
                                                ├─► service requests
       ┌────────────────────────────┐           ├─► F&B orders
       │  the gateway does:         │           ├─► PMS bridge
       │  · per-room tool filtering │           ├─► knowledge / RAG
       │  · scope injection         │           ├─► guest preferences
       │  · argument validation     │           └─► notification / escalation
       │  · result sanitisation     │
       │  · error normalisation     │      The agent can NEVER address these directly.
       │  · caching, audit          │      That is what makes tenant scoping mechanical
       └────────────────────────────┘      rather than a code-review question.

19. The MCP gateway

ResponsibilityWhat it prevents
Per-tenant tool filteringA property without curtains seeing a curtain tool the model will happily call

Argument validationInvented fields slipping through; every schema is strict, so unknown keys fail loudly
Result sanitisationStaff-authored menu text acting as a prompt injection vector

21. Tool error envelope

Every failure the agent sees is normalised into this shape. Errors are written as instructions, because a bare code produces an apology and a dead end while a suggestion lets the agent recover.

{
  "error": "NOT_AVAILABLE",
  "detail": "This room does not have motorised curtains.",
  "suggestion": "Tell the guest the curtains are manual. Offer to send housekeeping if they need help.",
  "retryable": false
}
CodeMeaningRetryable
NOT_AVAILABLERoom lacks the capability, or the item is off the menuNo
NOT_PERMITTEDPolicy refused itNo — and the agent is told not to rephrase
TEMPORARILY_UNREACHABLEHead-end or upstream not respondingYes
NEEDS_CONFIRMATIONT3 action needs a separate confirmed turnNo
INVALID_ARGUMENTSchema or bounds violationOnce, after correction
RATE_LIMITEDPer-device, per-stay or per-property limit hitLater
DUPLICATEA request of this kind is already openNo

22. Scope injection

What the model emits versus what actually executes:

{ // what the model emitted — note the room_id it invented
  "tool": "climate.set_temperature",
  "args": { "zone": "bedroom", "targetC": 23.0, "room_id": "999" }
}

{ // what the gateway executed
  "tool": "climate.set_temperature",
  "args": { "zone": "bedroom", "targetC": 23.0 },          // room_id STRIPPED
  "scope": {                                               // injected from the device identity
    "tenantId":   "t_demo_apac",
    "propertyId": "p_blr_whitefield",
    "roomId":     "r_412",
    "deviceId":   "d_412a"
  },
  "idempotencyKey": "sha256(turn_id | tool | canonical_args)"
}

Stripped, not validated. Any field matching a room, property, tenant or device pattern is removed before policy sees the call, and an attempt is recorded as a security signal.

Part VIICapability Model

23. How the surface is generated

The tool list is not fixed. It is generated per room from that room's capability manifest, which means a capability the room does not have produces no tool — so the model cannot propose it, no runtime check is needed, and no apology is ever generated for an action that was never possible.

  capability manifest (per ROOM TYPE, with per-room overrides)
        │
        ▼
  toolSurfaceFor(manifest)  ── drops tools whose capability is absent
        │                   ── narrows zone enums to the room's real zones
        ▼
  the tool list the agent is given for THIS turn

25. Property configuration

Onboarding a property is authoring one document, not writing code. The manifest attaches to room type, not room: a 300-room property has perhaps eight types, and authoring eight manifests with a handful of overrides is a day's work where authoring 300 is a project.

The vendor room reference is not the room number

vendorRoomId (e.g. INN-0412) is the automation system's own identifier and is resolved at onboarding. Assuming it equals the hotel room number is a classic integration bug whose symptom is actions landing in the wrong room.

Part VIIIGaps & Fixtures

26. What is not built

There is no staff or admin API

If you are building the staff or admin UI, there is currently nothing to call. The domain logic exists and is tested — listing open requests, acknowledging escalations, searching turn records, authoring manifests, flipping kill switches — but no HTTP layer is exposed over any of it, and there is no authentication or RBAC.

What a UI will need: a staff task API, an admin API for property/room/device and manifest authoring, an ops API for audit search and kill switches, a live event stream (SSE or WebSocket) so a housekeeping tablet buzzes when a ticket lands, and OIDC with per-property RBAC. That last one matters most: the staff API is the only inbound path in the entire design, and tenant-claim validation on every request is the control a chain's penetration test probes first.
