Set up before the meeting

Open a terminal in the repo and run npm install once. Have npm run turn ready to type. The demo needs no API key, no database and no internet — it runs entirely on a laptop, which is itself worth mentioning.

Part IThe one-minute version

Say this

“A guest in a hotel room says something out loud. We turn that into an action — adjusting their lights or temperature, raising a maintenance ticket, ordering food — and we say something back.

The old system matched what the guest said against a fixed list of phrases. If the phrase wasn't on the list, it failed. The new system uses an AI agent that actually reasons about the request, can read the current state of the room before deciding, and can handle two requests in one sentence.

The important part is not the AI. It's that the AI is not allowed to do anything on its own. It proposes an action; a separate component that never reads the guest's words decides whether that action is permitted. That's what makes it safe to put in forty thousand bedrooms.”

The three sentences that matter most

1
It understands, instead of matching. “It's freezing in here and can you fix the shower” is two requests, one of which needs a free-text description. The old system fails on that sentence. The new one reads the current temperature, works out the target, and raises the ticket.
2
A new hotel is configuration, not code. Every hotel uses a different room-automation vendor. We built an abstraction so the agent knows about “a thermostat with a temperature range” and never about Honeywell or Interel. Onboarding a property becomes a config file, not an engineering project.
3
The AI proposes; the platform decides. Every single action passes through a policy component that checks which room you're in, whether the action is permitted there, whether it costs money, and whether it needs the guest to confirm out loud. That component never reads the guest's words — so no matter what someone says to the device, they cannot talk it into doing something it isn't allowed to do.
If your manager asks only one question, it will be this

“What stops the AI doing something stupid or expensive?”

Answer: the AI has no ability to act. It can only suggest. A separate, small, independently tested component authorises every action, and it decides using structured data — which room, which tool, what it costs — not the guest's sentence. We have 93 automated tests, including 14 that specifically try to trick the system, and they run on every code change. A failure blocks the release.

Part IIWhat changed, and why

Lead with the failure, not the technology. The rebuild is justified by four concrete problems, and every one of them is something a colleague has seen.

Problem in V1What it looked likeWhat V2 does
Rigid phrase matching Dialogflow matched one sentence to one intent with fixed fields. “Make it a bit warmer” had no answer, because nothing could read the current temperature first. Everything unmatched became a fallback — and fallback rate is what decides whether guests use the device after day one. The agent reasons. It reads room state, handles several intents in one sentence, and writes a free-text description a technician can actually use.
Every hotel was a project Intents were wired straight to vendor APIs, so a hotel on Interel needed different code from one on Honeywell. Onboarding took weeks, and the marginal cost of a customer was engineering time. Abstract capabilities plus a per-property config file. Adding a vendor means writing one adapter; the agent, the prompts and the tests are untouched.
The device held cloud credentials The Android app ships Google and AWS keys. A device stolen from a guest room — which happens — is a credential breach, and the credential isn't limited to that room. The device holds nothing but a revocable certificate scoped to one room. This is the finding that would fail the first serious hotel-chain security review.
No record of why When a guest disputes a $180 room-service charge, V1 can show an API was called. It cannot show what was heard, what was decided, or on whose authority. Every turn produces an immutable record: what was heard (redacted), what was decided, which rule allowed it, and what happened. Written before the action runs.
Say this

“We didn't rebuild because the old system was old. We rebuilt because four things were structurally broken: guests couldn't speak naturally, every new hotel cost us engineering weeks, a stolen device was a security incident, and we couldn't explain our own decisions when a guest complained.”

Point out

“Notice the middle one. The guest never said a number. The system read that the room was set to 19.5 degrees, worked out that 'freezing' means warmer, and set 22.5. The old system could not do that sentence at all.

And notice the first one took 39 milliseconds and never called the AI. About 60% of what guests say is simple and repetitive, so we handle it deterministically. We only pay for AI reasoning when we actually need it.”

Act 2 — it refuses safely (2 minutes)

This is the act that matters to your manager.

npm run turn -- "who is staying in room 402" "unlock the door" \
                "set the temperature to 35 degrees" "I'm having chest pain"
guest    > who is staying in room 402
genie    > I can only help with your own room.

guest    > unlock the door
genie    > I'm not able to control the door lock. The front desk can help with that.

guest    > set the temperature to 35 degrees
tool     > climate.set_temperature [T1] DENY R6.out_of_bounds
           This property permits 18–26°C; 35°C is outside that.
genie    > I couldn't do that just now. Would you like me to connect you to the front desk?

guest    > I'm having chest pain
tool     > staff.escalate_urgent [T4] ESCALATE R4.escalate_to_human
state    > ESCALATED to staff
genie    > I'm alerting the hotel team right now. If this is an emergency please call 112 —
           I'm not able to call them for you. I'll stay here with you.
screen   > Emergency: 112 | Hotel team alerted
Point out — four different kinds of "no"

“Room 402 isn't refused by clever wording. There is no way to express it — no part of the system accepts a room number from the guest or from the AI. The room comes from the device's identity.

The door lock has no control in the system at any level. We decided a voice interface can't tell the guest apart from a stranger standing in the room, so we didn't build it.

The 35 degrees is a policy rule — that hotel allows 18 to 26. It's a config value, so a different hotel can set a different range without a code change.

And the last one: the device escalates to staff and tells the guest the truth about what it can't do. It never implies it has called an ambulance. That wording is a compliance requirement, not a style choice.”

Act 3 — a new hotel is configuration (2 minutes)

The same three words, three different rooms, three different outcomes — with no code involved anywhere.

npm run turn -- --device d_412a "close the curtains"   # Deluxe: no curtains
npm run turn -- --device d_511a "close the curtains"   # Suite: has curtains
npm run turn -- --device d_512a "close the curtains"   # Suite, motor broken
[d_412a] genie > I'm not sure about that one — would you like me to connect
                 you to the front desk?
[d_511a] tool  > curtains.set [T1] ALLOW ok
[d_511a] genie > Curtains closed.
[d_512a] genie > I'm not sure about that one — would you like me to connect
                 you to the front desk?
Point out

“Room 412 is a Deluxe with no motorised curtains, so the AI is never even offered a curtain control — it literally cannot propose one. Room 511 is a Suite and it works. Room 512 is also a Suite, but its curtain motor is awaiting replacement, so we switched that one capability off for that one room in a config file.

That's the whole onboarding story. A new hotel is a config file describing which rooms have what.”

Be honest about this one

The refusal wording for room 412 is weak — it should say “those curtains are manual” rather than a generic “I'm not sure”. If someone notices, say so: it is a known rough edge in the response wording, not a failure of the capability model. The important behaviour — that the action is impossible — is correct.

“Anything that costs money is frozen and read back with the total before we charge anything. When the guest says yes, we execute the exact order we froze — we don't re-interpret their 'yes'. Say this, walking the diagram

“Five steps. Who is this — the device tells us its identity and we look up which hotel and which room, and what that room is capable of. The guest never tells us their room number and neither does the AI.

What did they mean — if it's simple and common we answer instantly without AI. Otherwise the agent reasons about it.

Is it allowed — this is the important one. Separate component, checks every action against policy.

Do it — we send a vendor-neutral command and an adapter translates it for whatever system that hotel runs.

Check it worked — we read the state back. We only say 'done' when we've actually observed it done. If we're not sure, we say 'I've asked for that' instead. Confidently telling a guest the lights are off when they're still on is the fastest way to lose them.”

The one idea worth repeating

The model proposes; the platform disposes

The AI cannot act. It can only suggest an action. A separate component — small enough that a person can read all of it, with its own 27 tests — authorises every suggestion using structured facts: which room, which action, what it costs, what time it is.

It never reads the guest's sentence. That's the whole trick. Someone can say anything they like to the device — and people will try — but the component that decides never saw their words, so there is nothing to persuade.

Worst case if the AI is completely fooled: it says something embarrassing, or adjusts the lights in the caller's own room. It cannot reach another room, cannot spend money without a separate spoken confirmation, and cannot touch anything we classified as unsafe.

The whole integration

connect once, keep it open:   ws://gateway:8443

send  { "type":"hello", "deviceId":"d_412a" }
recv  { "type":"ready", "property":"…", "room":"412", "assistantName":"Voice Genie" }

send  { "type":"turn", "transcript":"turn on the lights", "asrConfidence":0.94 }
recv  { "type":"ack",   "filledPause":"Let me sort that—" }     ← play immediately
recv  { "type":"speak", "text":"Done.", "turnId":"turn_…" }     ← then this
recv  { "type":"screen","text":"…" }                            ← optional
Three things to tell them explicitly
  • One connection per device, kept open. Not one per request. Opening a connection each turn adds a third of a second to every interaction.
  • Play ack the moment it arrives. It comes back before the real answer. That's what makes the device feel instant even when the AI is thinking. Getting this wrong makes a good system feel slow.
  • Send the real ASR confidence. Below 0.6 we ask the guest to repeat instead of guessing at an action. If you hardcode it, we guess when we shouldn't.
And one change that isn't optional

The current app ships Google and AWS credentials and calls speech recognition directly. Those have to come out. Once the app talks to us instead, a stolen device yields nothing but a certificate we can revoke — and we can change speech vendor or tune accuracy without shipping a new APK.

Staff / admin UI team — read this first

There is nothing for you to call yet. Say this plainly.

The logic exists and is tested — listing open requests, acknowledging escalations, searching what the assistant did, switching capabilities off. But none of it is exposed over HTTP, and there is no login. If the UI starts next sprint, this API is the blocker.

Say this

“Before I build it I need two answers from the UI team: REST or GraphQL, and which login provider we're standardising on. Both change the shape enough that I'd rather not guess.”

Ticketing and operations team

The important question is not technical.

Ask the room

“Do our hotels want maintenance tickets inside Woohoo, or pushed into the system they already use? Because most hotels already run HotSOS or Quore, and no hotel wants a second queue for their staff to watch.”

We produce a well-described event every time something happens — a request raised, an order placed, an emergency escalated, a device going offline. Consuming it means receiving a small JSON message. The design supports either direction: we can hold the tickets, or we can push them to you and hold nothing.

Automation and PMS teams

Both work the same way: you implement a small interface, and nothing above it changes.

connect(property)          // open a session with that hotel's system
readRoomState(room)        // what is the room doing right now
applyCapability(room, op)  // "set the bedroom to 23" — vendor-neutral in, result out
health()                   // are you reachable
conformanceSuite()         // prove it works before a property goes live
The rule that keeps this clean

Vendor language stops at the adapter. Nothing above it may mention Honeywell, Interel, BACnet objects or KNX group addresses. Your adapter receives “set the bedroom setpoint to 23” and translates it. If a room's curtain motor is open/close only, your adapter handles a request for 40% — the AI never learns the difference.

There is a full simulator, so you can build and test your adapter with no hotel hardware at all. It even fakes the awkward cases: slow responses, dropped connections, and writes that acknowledge but don't actually take effect.

One thing the automation team must plan for

These systems live inside the hotel, behind the hotel's firewall, with no route from the internet — and hotel IT will not open one. So we need a small appliance on site that connects outward to us. It also means the lights still work when the hotel's internet drops, which happens more than anyone likes. That appliance is real hardware to buy, ship and support, and it should be in someone's plan.

Part VIIQuestions you'll get, and decisions you need

Likely questions

QuestionAnswer
What if the AI does something wrong?It can't act. It proposes; a separate component authorises. The worst case if it's completely fooled is an odd sentence or a light change in the caller's own room.
What if someone tries to trick it?They will — some will film it. We have 14 tests that actively attempt it, and they must all pass before any release. The defence isn't clever wording, it's that the deciding component never reads what the guest said.
Can it hear us all the time?No. Nothing leaves the room until the wake word fires, and that runs on the device. We never store recordings anywhere — audio exists only while it's being transcribed.
What happens when the internet drops?The on-site appliance keeps lights, temperature and do-not-disturb working, the device says it's offline, and requests are queued and sent when it comes back.
What if the AI provider goes down?We fall back to handling the common requests without AI and tell the guest what still works. The route to a human always stays open.
Can it unlock the door?No, deliberately, and we should keep saying no. A voice can't tell a guest apart from a stranger standing in the room.
How long to add a hotel?Target is five working days once the adapter for their vendor exists — it's a config file and an appliance. The first hotel on a new vendor takes longer because we build that adapter.
Is guest data safe?We don't keep recordings, we mask personal details before anything is stored, card numbers are blocked outright, and each region's data stays in its region.
Why not just use ChatGPT/Gemini directly?That's the easy 20%. The other 80% is making sure it can only ever act on the right room, within limits, with a record of why — and that's what we built.
