Two modelling decisions worth defending

The voice device is not the room, and is bound to it revocably. Modelling WOOHOO_HUB as a separate entity with an explicit, timestamped, re-verifiable binding to ROOM is what makes the mis-binding detection in §22 possible. Collapsing them — treating the device ID as the room ID — is the shortcut V1 took and it is why a moved device becomes an invisible bug.

The capability manifest attaches to room type, not room. A 300-room property has perhaps eight room types. Authoring eight manifests with a handful of per-room overrides is a day's work; authoring 300 is a project. This single choice is most of the difference between five-day and five-week onboarding.

37. Device state: cache, twin and truth

State consistency is where in-room automation systems quietly break. The BMS is the source of truth, but reading it on every turn is too slow and too fragile.

   TRUTH                      SHADOW                        CACHE                    AGENT
   ───────────                ──────────────                ────────────             ─────────
   BMS head-end   ──push/──►  Edge Gateway     ──stream──►  Redis (cloud)  ──read──►  room.get_state
   (INNCOM/       ◄─write──   local shadow     ◄─command──  device-state             (pre-fetched)
    Interel)                  + last-known                   service
                              + staleness ts

   Freshness contract:
     • fresh   < 10s   → agent uses it silently
     • stale   10–120s → agent uses it but the adapter issues a verify-read after any write
     • expired > 120s  → device-state service forces a synchronous read before answering;
                         if that read fails, the tool returns UNKNOWN and the agent says so
                         ("I'm not sure what it's set to right now — shall I set it to 22?")

   Write path:   agent → PDP → device-state.set → adapter → edge → BMS
                 → BMS confirms → shadow updated → verify-read → agent confirms to guest
                 If no confirmation within 2.5s: agent says "I've asked for that" (not "done"),
                 and a follow-up screen update lands when confirmation arrives.
Never say “done” on an unconfirmed write

The most damaging failure mode in a voice automation product is the confident false confirmation. The guest hears “I've turned off the lights”, the lights stay on, and the product is dead to that guest. The state machine above exists entirely to make the assistant's confidence proportional to its evidence — “done” when verified, “I've asked for that” when pending, “I couldn't reach the room system” when failed. Encode this in the response templates so it cannot be forgotten.

Phase 1: NATS JetStream in Docker — one dependency, durable, trivially local. Phase 2: EventBridge for routing + SQS for durable per-consumer queues. Kinesis/MSK only for the device-state telemetry firehose if its volume justifies it, and not before.

Every event carries tenant_id, property_id, trace_id and a schema version. Without tenant_id on the envelope, per-tenant filtering, cost attribution and regional routing all become impossible to add later without a migration.

39. Room automation vendor adapters

Each property runs exactly one automation vendor — which is a considerable simplification and should be preserved as an invariant, not softened. It means an adapter never has to reconcile two sources of truth for the same room.

39.1 The adapter contract

interface AutomationAdapter {
  // Identity
  vendor: "inncom" | "interel" | "bacnet" | "knx" | "lutron" | "simulator";

  // Lifecycle
  connect(property: PropertyBinding): Promise<ConnectionHandle>;

  conformanceSuite(): ConformanceTest[];

Build the simulator before the second real adapter

The single biggest velocity constraint on this project will be access to real hotel hardware. A high-fidelity simulator — one that models latency, intermittent failures, slow acknowledgements and state that drifts because a housekeeper touched a wall switch — lets the whole team work without booking a room. It is also the only way to test the degradation ladder, since you cannot ask a hotel to unplug its BMS.

40. The on-premise edge gateway

You did not list this as a component. It is nonetheless the one that most determines whether this product works, because the systems it talks to are not on the internet and will not be put there.

40.1 Why it is not optional

  • INNCOM and Interel head-ends are LAN-resident, typically on an isolated building network with no outbound route and certainly no inbound one.
  • Hotel IT will not open inbound firewall ports for a vendor, and the request itself will delay onboarding by months.
  • Round-tripping every light command to a cloud region adds 60–200 ms to an action whose entire budget is under a second.
  • When the property's WAN drops — which is routine — the guest must still be able to turn on the lights. Only something inside the building can deliver that.

40.2 Fleet management

You are now shipping hardware to hundreds of buildings you do not control. That needs: zero-touch provisioning (device boots, calls home, receives its property binding and config); staged, signed, A/B firmware updates with automatic rollback on health-check failure; remote diagnostics without inbound access; a physical spares strategy with the hotel's engineering team; and a clear runbook for “the appliance is dead and the GM is calling”. AWS IoT Greengrass is a credible base for this and is worth evaluating against a simpler bespoke agent — the trade is capability against another large dependency on the critical path.

42. Service request and ticketing

This is where the product earns its keep operationally, and where the agentic approach is most obviously better than intent matching — a free-text description written by a model that understood the guest is far more useful to a maintenance technician than a category code.
