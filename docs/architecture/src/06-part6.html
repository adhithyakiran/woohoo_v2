30. Why an MCP gateway is mandatory

You already expose hotel, room, device and service data as MCP servers. The instinct is to point the agent at them directly — that is what MCP is for. For a single-tenant developer tool, that instinct is right. For a multi-tenant system that actuates physical devices in strangers' bedrooms, it is wrong, and the reasons are worth being precise about.

Problem with direct agent→MCPWhat goes wrongWhat the gateway does instead
Scope enforcementIf the agent calls the Device State server directly, then the arguments — including which room — come from model output. A prompt injection or a model error can address another room. Nothing structural prevents it.The gateway injects tenant/property/room from the authenticated TurnContext and strips any scope fields the model supplied. Cross-room addressing becomes impossible rather than unlikely.
Per-tenant tool visibilityEvery hotel sees every tool. A property without curtains gets a curtain tool the model will happily call.The gateway filters the advertised tool set by the property's capability manifest before the agent ever sees it.
Result sanitisationTool results flow straight into the model's context. A menu description edited by a hotel employee is an injection vector.All results are wrapped in untrusted-content fencing and scanned before entering context (§46).
Connection managementN servers × M concurrent turns = connection explosion, per-turn handshakes, unbounded latency.Pooled, warm, multiplexed connections with per-server circuit breakers.
CachingThe property catalogue is read on every turn and changes weekly. Without a cache, it is the hottest and most wasteful query in the system.Per-tool cache policy with declared TTLs and explicit invalidation on catalogue events.
Uniform auditEach server logs differently, or not at all.One place records every tool call, its arguments, its verdict, its latency and its result digest.
Error shapingRaw vendor errors reach the model. “INNCOM: ERR_0x8004” produces either a hallucinated explanation or a useless apology.Errors are normalised into a small vocabulary the model is trained by the prompt to handle: NOT_AVAILABLE, NOT_PERMITTED, TEMPORARILY_UNREACHABLE, NEEDS_CONFIRMATION, INVALID_ARGUMENT.
Schema versioningChanging a tool schema breaks prompts silently and only in production.Schemas are versioned artefacts pinned per prompt version, validated in CI by the eval harness.
Confused deputyThe agent's credentials are broad; a downstream server cannot tell whether a call reflects a guest's request or an injected instruction.Per-turn, audience-bound, short-lived tokens carrying the exact scope, minted by the gateway.
Decision D9 — MCP Gateway

The agent holds exactly one MCP connection: to the internal MCP Gateway. Downstream MCP servers are never addressable by the agent runtime. The gateway is the tool plane's control point — registry, filter, scope injector, sanitiser, cache, circuit breaker and audit point — and it is where the “the model proposes, the platform disposes” principle is made mechanical.

31.1 Should vendor adapters be MCP servers?

No. This is worth stating plainly because it is a tempting symmetry. MCP is a protocol for exposing capabilities to a model. The automation adapters must never be visible to the model — the entire point of principle P4 is that the agent reasons about “a thermostat with a setpoint” and has no concept of INNCOM. If inncom-adapter were an MCP server, its vendor-shaped tools would leak into the model's world and the abstraction would be dead within two sprints.

The adapters sit behind the Device State MCP server, which presents a single vendor-neutral surface. Adding Schneider or Lutron support means writing an adapter and a capability mapping. The model's tool list does not change — and the prompt, the evals and the fast-lane grammar all keep working untouched.

31.2 Transport and deployment

LinkTransportRationale
Agent → MCP GatewayStreamable HTTPSingle stable endpoint; supports streaming results; works across process and later across network without a code change.
Gateway → MCP servers (Phase 1)In-processSame container. Zero network latency. The interface is still the MCP tool contract, so promotion is a config change.
Gateway → MCP servers (Phase 2+)Streamable HTTP over mTLS in-VPCOnce servers are separately deployed. Avoid stdio in production — it couples process lifecycles and makes scaling and observability awkward.
Third-party / customer MCP serversStreamable HTTP, OAuth 2.1 resource server, sandboxedNot in Phase 1 or 2. When a chain wants to plug in its own MCP server, it must be strictly quarantined: separate network egress policy, results treated as maximally untrusted, no T2+ tools, per-tenant allowlist. Admitting third-party tool servers into an agent that controls hardware is a security decision, not an integration decision.

32. Tool surface design

Tool design is the highest-leverage thing you will do in this system. A well-shaped surface makes a mid-sized model reliable; a badly shaped one makes the best model unreliable.

32.1 Design rules

RuleWhy
Keep the surface under 25 toolsSelection reliability degrades as the tool list grows, and every schema is input tokens on every turn. If you need more, you have a capability-modelling problem, not a tool-count problem.
Name by guest intent, not by systemclimate.set_temperature, not hvac.write_setpoint_register. The model reasons better about names that match how the request was phrased.
Return the resulting state, alwaysEvery mutating tool returns the new observed state. This eliminates a read-back round-trip and lets the agent confirm truthfully.
Make read tools cheap and batch themOne room.get_state() returning everything beats five per-device reads. It is also what the pre-fetch calls.
Errors must be instructions{"error":"NOT_AVAILABLE","detail":"This room has no motorised curtains.","suggestion":"Offer to open them manually or contact housekeeping."} lets the model recover gracefully. A bare error code produces an apology and a dead end.
Idempotency on every mutationRetries are inevitable across a flaky BMS link. Key on (turn_id, tool, canonical_args).
No tool takes a room or property identifierScope is ambient (P2). If a schema has a room_id field, someone will eventually let the model fill it.
Enumerate where possibleZones, categories and priorities as enums drawn from the room's actual configuration, not free strings. Constrains the model into validity.
Free text only where judgement is requiredA maintenance description should be free text. A temperature should never be.

33.1 The three levels

  1. Capability — an abstract, vendor-neutral ability with a typed contract: climate.setpoint with a range and unit; curtains.position with 0–100; curtains.open_close as binary. Capabilities are defined once, globally, and versioned.
  2. Capability manifest — per room (usually per room type, with per-room overrides), declaring which capabilities exist, which zones they apply to, what the bounds are, and which driver serves them. This is data, authored during onboarding, versioned, and diffable.
  3. Driver mapping — per vendor, the translation from capability operation to concrete protocol operation. Lives entirely inside the adapter. The model, the prompt, the evals and the fast lane never see it.
Decision D10 — Capability model

The tool surface presented to the model is generated from the room's capability manifest at context-assembly time. A capability the room does not have produces no tool, so the model cannot propose it, so no runtime check is needed and no apology is ever generated for an action that was never possible. Graceful degradation between capability levels (position control vs binary open/close) is handled in the adapter, not by the model.

The corollary: the manifest is a first-class product artefact. It needs an authoring tool, a validation schema, a diff view, a version history and a conformance test suite that can be run against a real property before go-live. Budget for this properly — it is the thing that determines whether onboarding takes five days or five weeks.

34. Authorization, scoping and idempotency

34.1 Scope injection

// What the model emits
{ "tool": "climate.set_temperature",
  "args": { "zone": "bedroom", "target_c": 23.0, "room_id": "999" } }   ← model-supplied scope

// What the gateway executes  — model-supplied scope fields are STRIPPED, not validated
{ "tool": "climate.set_temperature",
  "args": { "zone": "bedroom", "target_c": 23.0 },
  "scope": {                                    ← injected from the authenticated TurnContext
     "tenant_id":   "t_marriott_apac",
     "property_id": "p_blr_whitefield",
     "room_id":     "r_412",                    ← from the device certificate, never from the model
     "device_id":   "d_8f2a...",
     "turn_id":     "turn_01J...",
     "actor":       "guest",
     "consent":     { "voice": true, "prefs": false }
  },
  "idempotency_key": "sha256(turn_01J... | climate.set_temperature | {zone:bedroom,target_c:23.0})"
}

Stripped, not validated is deliberate. Validating a model-supplied room_id against the real one means the field exists in the schema, which means it can be populated, which means somebody will one day “temporarily” trust it for a staff feature. Removing the field from the surface entirely removes the class of bug.

34.3 Idempotency and retry

  • Every mutating tool call carries an idempotency key derived from (turn_id, tool, canonical_args). Replaying the same key returns the original result rather than acting twice.
  • Retries are only automatic for tier T0–T1 (read and reversible-physical). T2 and above are never silently retried — a duplicate maintenance ticket is annoying, a duplicate $200 room-service order is a chargeback.
  • Retry budget: 2 attempts, 150 ms and 400 ms, jittered, and only within the turn's wall-clock budget.
  • Circuit breaker per (property, vendor): 5 failures in 30 s opens it for 60 s. While open, the capability is reported as TEMPORARILY_UNREACHABLE and the agent offers the staff path. One hotel's dead head-end must never consume the adapter's capacity for every other property.
