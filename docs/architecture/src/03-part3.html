10. Modular monolith vs microservices — the honest answer

You asked whether this should be modular, whether it should be microservices, and which components must be split. The honest answer has three parts, and the middle one is the one most teams get wrong.

10.1 It must be modular. That is not the same as distributed.

Modularity is non-negotiable here, because the whole product thesis is that a new hotel is configuration rather than code. That requires hard internal boundaries: the agent must not be able to reach into the INNCOM adapter, the F&B service must not read the property catalogue's tables directly, and vendor knowledge must be physically incapable of leaking into the reasoning layer. But every one of those boundaries can be enforced by a module system, a package structure and a lint rule — they do not require a network hop.

10.2 Most of it should not be separate services at Phase 1.

Splitting a system into microservices buys you three things: independent scaling, independent deployment, and failure isolation. It costs you distributed transactions, network failure modes between every pair of components, N× observability plumbing, N× CI pipelines, and — the one that actually kills small teams — the inability to change an interface without a coordinated multi-repo release.

At Phase 1 you have one pilot property and a handful of engineers. The scaling asymmetries that justify a split do not exist yet, and the interfaces are going to change weekly because nobody has yet learned what the agent actually needs from the catalogue. Splitting now means paying the full cost of distribution to buy benefits you cannot use.

10.3 But four things must be separate from day one, for reasons that are not about scale.

Decision D13 — Service granularity

Phase 1 ships five deployable units: (1) woohoo-core, a modular monolith containing the orchestrator, router, agent runtime, MCP gateway and all domain services; (2) device-gateway; (3) policy-service; (4) one automation-adapter-* per vendor; (5) edge-gateway (ships to properties). Everything inside woohoo-core communicates through explicit in-process interfaces that are shaped like network calls — typed request/response, no shared mutable state, no cross-module database access — so that promoting any module to a service later is a transport change, not a redesign.

Split triggers — the rule that keeps this honest

A module is promoted to a service when one of these is measurably true, and never because it feels cleaner:

  • Scaling asymmetry: the module's resource curve diverges >3× from its host (e.g. device-state write volume forcing the whole core to scale out).
  • Deploy contention: two teams block each other more than twice a week, or a release cadence conflict emerges (prompt changes daily vs domain code weekly).
  • Blast radius: the module can exhaust a shared resource — thread pool, connection pool, memory — and take the host down. This is the PMS-bridge and automation-adapter case.
  • Security boundary: the module starts handling untrusted third-party code or data (customer-supplied MCP servers).
  • Compliance boundary: the module's data must live in a different jurisdiction or under a different key than its host.

Write the trigger into the module's README when you create it. Review the list quarterly. This turns “should we split?” from an architecture debate into a metric lookup.

13. Synchronous vs event-driven boundaries

Getting this wrong is the most common way agentic systems become unreliable: teams make the guest-facing path asynchronous for elegance, and then cannot tell the guest whether their request worked.

FlowModeReasoning
Device → Gateway → Orchestrator → ASR → Router → AgentSynchronous / streamingThe guest is standing there. Every millisecond is visible. No queues on this path, ever.
Agent → PDP → MCP Gateway → domain serviceSynchronousThe agent needs the result to compose its reply. A queue here means the agent must speculate about outcomes, which is exactly the hallucination failure mode.
Automation command → adapter → edge → BMSSynchronous with a hard 2.5 s budget, then async continuationMost BMS writes ack in 150–800 ms. If it exceeds budget, the agent says “I've asked for that — give it a moment” and the confirmation arrives later as a screen update and, optionally, a follow-up utterance. Never block the voice turn on a slow head-end.
Ticket created → staff notificationAsync (event)The guest does not need to wait for a housekeeper's tablet to buzz. Durable delivery matters more than latency.
Device state telemetry ingestAsync (event)High volume, no guest waiting, eventual consistency acceptable. Backpressure here must never reach the voice path.
Audit record writeAsync, but sealed synchronouslyThe record is constructed and sealed in the turn; the durable write is queued. Critical nuance: policy verdicts are appended before execution (see §7), so a crash cannot erase evidence of what was authorised.
Folio postingAsync with saga semanticsMoney. Needs idempotency keys, retries, compensation, and reconciliation against the PMS. Must never be a fire-and-forget event.
Analytics / quality metricsAsync, sampledFirehose to S3, batch aggregate. Never on the hot path.
The rule

If the guest is waiting for the answer, it is synchronous. If the guest has already been told, it is asynchronous. The dividing line is the moment the agent finishes speaking, and it is the responsibility of the Session Orchestrator to know which side of that line every operation is on.
