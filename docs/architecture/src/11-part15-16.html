Two things to insist on in Phase 1

The device simulator and the adapter simulator are first-class deliverables, not test scaffolding. Without them, every engineer needs hardware and a hotel, and the team's velocity is capped by physical logistics. With them, the whole system is testable on a laptop and in CI.

Same dashboards, same instrumentation, same images as production. If the Docker stack uses different observability than AWS, you will debug production with tools you have never used. OpenTelemetry everywhere makes this free.

76. The cross-cloud question

The agent runtime will sit on AWS while the model sits on Google Cloud. This deserves a decision rather than drift.

OptionProsCons
A. All on AWS, call Vertex over the internet ChosenOne estate to operate, secure and certify. One IaC stack. Simplest for a small team. Egress cost is negligible (text only).Adds internet RTT to the LLM call — typically 20–60 ms when both are in the same geography. Cross-cloud auth to manage.
B. Agent runtime on GCP, rest on AWSLowest LLM latencyTwo clouds to secure, certify, monitor and pay for; a network hop for every tool call instead of every LLM call — and there are more tool calls than LLM calls. Doubles the compliance surface.
C. All on GCPSingle cloud, lowest LLM latencyAbandons the AWS plan, the IoT Core fit and existing AWS familiarity. Only reconsider if Gemini becomes a much deeper dependency.
Decision D20 — Option A, with measurement

Keep everything on AWS and call Vertex AI over the internet from the same geography (ap-south-1 → asia-south1, eu-west-1 → europe-west1, and so on). Authenticate with Workload Identity Federation so no Google service-account key file exists anywhere in the estate.

Measure the added latency in the pilot rather than assuming it. Instrument the llm.generate span's TTFT specifically and compare against a same-cloud control. If cross-cloud RTT turns out to consume more than ~15% of the agentic lane's p95 budget, revisit — but do not pre-optimise a hop that is probably 40 ms in a 1,900 ms budget.

77. CI/CD and prompt release management

The most important idea in this section: a prompt change is a production deployment. Systems that treat prompts as content rather than code fail in production in ways that are hard to diagnose, because the artefact that changed was never versioned.

 ARTEFACT TYPES — all versioned, all released the same way
 ├── container images        (services)
 ├── prompt bundles          (Layer 0/1 templates, refusal policy, response templates)
 ├── tool schemas            (the MCP tool surface definitions)
 ├── model pins              (model IDs + generation config per lane)
 ├── policy bundles          (risk tiers, property policy defaults, PDP rules)
 ├── capability manifests    (per property — released per property, not fleet-wide)
 └── phrase packs            (per property voice × language, pushed to devices)

 PIPELINE
   commit ──► build + unit ──► integration (against simulators) ──► EVAL GATE ──► staging
                                                                       │
                       golden 100% · adversarial 0 failures · safety 0 failures
                       latency within +10% · capability matrix green
                                                                       ▼
   staging soak (24h, synthetic traffic) ──► CANARY PROPERTY (1 real hotel, opted in)
                                                  │  24–72h, watched metrics:
                                                  │  fallback rate, escalation rate, task success,
                                                  │  latency p95, policy denials, guest ratings
                                                  ▼
   progressive rollout: 5% properties → 25% → 100%, with automatic halt on metric regression
                                                  ▼
   ROLLBACK: pin previous prompt/model/policy version — config change, effective next turn,
             no deploy required. Target: under 60 seconds from decision to effect.
Rollback must not require a deploy

When a prompt change starts producing bad behaviour across 40,000 rooms at 22:00 on a Friday, you need to revert in under a minute. If reverting means rebuilding a container and waiting for a rolling deploy, you will instead spend fifteen minutes with a live incident. Make prompt, model and policy versions runtime configuration resolved per turn, with a pin that propagates through the same sub-10-second config channel as the kill switches.

Buy the lab hardware

A bench with a real INNCOM controller and a real Interel controller, wired to actual dimmers, a thermostat and a curtain motor, is one of the highest-return purchases on this project. Vendor systems have undocumented behaviours — write timing, acknowledgement semantics, priority handling, what happens when two writes race — that no simulator will reproduce until you have observed them. Discovering them in a guest room is expensive; discovering them on a bench is Tuesday.

Sequencing advice

Phases 1 and 2 must run in parallel, and Phase 2 is the one that will slip — hardware, vendor access and firmware always take longer than expected. Start the device and edge work first if you can only start one, because the agentic core can be developed against simulators indefinitely while the device work cannot.

Do not let the pilot property be a flagship. Pick a mid-tier property with a co-operative engineering manager, a modern BMS install, and a GM who will tolerate a bad week. Your first flagship deployment should be your fourth property, not your first.
