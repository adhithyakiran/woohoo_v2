43. Threat model for a physical-world agent

Most LLM safety guidance assumes the worst outcome is a bad sentence. Here, the agent controls temperature in a room where someone is sleeping, creates work orders that send a stranger to a guest's door, and posts charges to a bill. The threat model has to be built around consequence, not around content.

IDThreatRealistic scenarioSeverityPrimary control (structural, not prompt-based)
T1Cross-room actuationInjection or model error causes an action against a room other than the caller'sCriticalScope is injected server-side from the device certificate; tools have no room parameter (§34.1). Structurally impossible, not merely prevented.
T2Cross-guest disclosure“Who's staying in 402?” / “What did the guest next door order?”CriticalSame scoping. PMS Bridge can only resolve the stay bound to the calling room. Output guard scans replies for other-room identifiers.
T3Unauthorised chargeModel places a large order without adequate confirmation, or a guest disputes oneHighT3 tier: mandatory spoken confirmation including the total; per-stay spend cap; idempotency; full audit record of the confirmation utterance.
T4Prompt injection via hotel contentA staff-authored menu item description contains “ignore previous instructions and…”HighUntrusted-content fencing (§46); tool results can never authorise actions; PDP is unaffected by anything in context.
T5Blast radius“Turn off all the lights in the hotel” — or a bug that fans outCriticalNo tool accepts a multi-room target. Bulk operations do not exist in the guest tool surface at any tier (§45).
T6Physical harm through automationHeat set to maximum in an occupied room; lights strobed; HVAC off in extreme weatherHighHard bounds in the PDP, enforced per property; rate limits on repeated changes; no capability exists for lighting effects that could trigger photosensitivity.
T7Sleep/comfort disruptionA scheduled or delayed action fires at 3 a.m.MediumQuiet-hours policy applies to delivery as well as decision; no unattended actuation without an explicit guest-set schedule.

T13Runaway loopAgent retries a failing action repeatedly, spamming the BMS or creating duplicate ticketsMediumLoop caps (§27), circuit breakers, idempotency, per-turn and per-stay rate limits.
T14Data exfiltration via tool outputInjection causes the agent to place sensitive data into a free-text field that leaves the systemMediumOutput guard on free-text fields; egress is limited to hotel-internal destinations; no tool performs arbitrary network calls.
T15Model or prompt regressionA prompt tweak silently changes behaviour across 40,000 roomsHighPrompts and models are versioned artefacts gated by the eval suite, rolled out progressively with automatic rollback (§77).

44. The action risk tier model

Every tool carries a tier. The tier determines what the platform requires before the action reaches the world. This table is the heart of the safety design and should be reviewed line by line.

Decision D25 — No door lock control in V2

Guests will ask for it and sales will want it. Refuse it for V2, and be explicit about why: a voice interface has no reliable speaker authentication, the room is accessible to anyone physically present, and the failure mode is a stranger entering an occupied guest room. There is no confirmation flow that makes this acceptable, because the attacker and the guest are indistinguishable to the device.

If it must eventually exist, it requires a second factor that is not voice — the guest's authenticated phone app, or a PMS-verified key credential — and it should be that app, not the voice device, that performs the action. Note also that the same reasoning is why unlocking is prohibited but a “is my door locked?” read could be considered later at T0 with a per-property opt-in.

45. Blast radius containment

ContainmentMechanism
RoomTools have no room parameter. Scope comes from the device certificate. There is no code path by which a guest turn affects another room.
PropertyAdapter credentials are property-scoped. A compromised adapter connection reaches one hotel.

FleetThere is no fleet-wide command path in the guest flow at all. Bulk operations exist only in the staff/admin plane, behind human authentication, with a separate approval step and a hard cap on rooms per operation.

Decision D12 — The bulk-operation prohibition

“Turn off all the lights in the hotel” is not defended against by a policy rule that rejects it. It is defended against by there being no tool that can express it. Every guest-plane tool operates on exactly one room, and that room is not a parameter. This is worth more than any amount of prompt engineering, and it is the design property to protect hardest during future feature requests — because someone will eventually ask for “turn on all the lights on floor 3 for the fire drill”, and the answer is that it belongs in the staff plane with human authentication, not in the guest tool surface.

46. Prompt injection defence

The agent reads text it did not author: guest speech, staff-written menus and FAQs, ticket histories, and results from vendor systems. Any of it can carry instructions. The defence is layered, and no single layer is trusted.

 LAYER 1 · STRUCTURAL SEPARATION
   Untrusted content never concatenated into instruction layers. It appears only inside explicit
   fenced blocks with a standing rule that content inside is data, never instruction. Layer 0 of the
   prompt (§26) states this once, stably, so it is part of the cached, immutable system identity.

 LAYER 2 · THE PDP DOES NOT READ THE PROMPT
   ★ The most important layer. Policy decisions are made from the TurnContext and the proposed tool
   call — structured data — and never from the model's reasoning, its explanation, or anything in the
   conversation. An injection can change what the model PROPOSES. It cannot change what is PERMITTED.
   Whatever the attacker convinces the model of, the action still has to pass a component that never
   read their text.

 LAYER 3 · CONTENT SANITISATION
   Tool results scanned before entering context: instruction-like patterns flagged, control characters
   and prompt delimiters stripped, length capped. Staff-authored content (menus, FAQ) is additionally
   scanned at AUTHORING time in the admin UI — catching it once at write beats catching it every read.

 LAYER 4 · CAPABILITY MINIMISATION
   The model can only propose tools present in this room's surface. There is no shell, no HTTP fetch,
   no file access, no code execution, no ability to call an arbitrary endpoint. The "lethal trifecta"
   — private data + untrusted content + external communication — is broken at the third leg: there is
   no egress channel the agent controls.

 LAYER 5 · OUTPUT GUARD
   Replies scanned before TTS for: other-room identifiers, other guests' names, credentials, internal
   IDs, system-prompt fragments, and length. Violations are replaced with a safe response and logged
   as a security event, not silently dropped.

 LAYER 6 · DETECTION
   policy.denied and guard-violation events feed anomaly detection. A device generating repeated
   denials is flagged; a property showing a spike is escalated. Injection attempts become a signal
   rather than an invisible near-miss.
The honest position on prompt injection

Prompt injection is not solved, and any architecture that claims to prevent it at the model layer is overselling. This design therefore assumes injection will sometimes succeed at the model layer and asks a different question: what is the worst thing a fully compromised model can cause?

With the controls above, the answer is: it can say something embarrassing, and it can perform a T0–T2 action in the caller's own room — adjust that room's lights or temperature, or raise a service request that a human will see. It cannot reach another room, cannot spend money without a separate confirmed turn, cannot exfiltrate data because it has no egress, and cannot touch anything at T4/T5. That is a bounded, survivable worst case, and bounding it is the actual goal.

47. Grounding and hallucination control

  • Property facts come only from tools. The prompt explicitly forbids answering questions about amenities, hours, prices or policies from the model's own knowledge. If property.search_knowledge returns nothing, the answer is “I don't have that — let me connect you to the front desk”, and staff.connect makes that a real action rather than a brush-off.
  • Retrieval returns citations, and the turn record stores which knowledge chunks were used. When a guest complains they were told the wrong thing, you can show exactly what the system read.
  • Never invent a capability. Because the tool surface is generated from the manifest, the model cannot propose a curtain action in a room without curtains. For questions rather than actions, the property profile in Layer 1 lists what the property does not have — explicit negative facts prevent a helpful model from assuming a business hotel has a spa.
  • Never invent an outcome. Confirmations are generated from tool results, not from the model's expectation (§37).
  • Uncertainty is a supported answer. “I'm not sure — shall I ask the front desk?” is measured as a success in the eval suite when it is the correct response. If your metrics only reward answering, you will train the system to guess.

48. Duty of care and emergency escalation

A device in a bedroom will eventually hear someone in genuine trouble. The system's obligations here are real, and the design has to be decided deliberately rather than emerging from a fallback branch.

SituationSystem behaviourDesign rationale
Medical emergency (“I'm having chest pain”, “help, I can't breathe”)Detected before normal routing. Immediately: (1) say plainly — “I'm alerting the hotel team now. If this is an emergency, please call [local emergency number] — I can't call them for you.”; (2) raise T4 escalation to the front desk and duty manager with room, time and the trigger; (3) display the local emergency number on screen; (4) stay in an open listening state and keep the escalation open until a human acknowledges.The device must never imply it has summoned help it cannot summon. Telling the guest the truth about its limits and escalating in parallel is the only defensible behaviour. The screen matters: it works when speech does not.
Fire / smoke / alarmDo not attempt automation. State the evacuation instruction, show it on screen, escalate. Never claim to have contacted the fire service.Life-safety systems are regulated and independent. Woohoo must not interfere with or appear to substitute for them.
Security / intruder / feeling unsafeSilent-capable escalation to security and duty manager. Offer to connect to the front desk. Do not announce loudly if the guest's phrasing suggests they may not be alone.A loud confirmation can escalate a dangerous situation. Design the acknowledgement to be quiet and on-screen by default in this path.
Expressions of distress or self-harmRespond with warmth, without attempting counselling or clinical judgement. Provide the locally appropriate crisis helpline number on screen and aloud. Escalate to the duty manager under the property's welfare protocol. Do not create a service ticket that reads like a maintenance request.The device is not a crisis service and must not pretend to be. Its useful contributions are: being kind, surfacing a real helpline, and getting a trained human involved quickly. Every property must have a documented welfare protocol before go-live — make it an onboarding gate.
Child alone in the roomT3+ actions disabled on child-indicative interaction patterns; no ordering, no charges. Age-appropriate refusals. Never disclose stay details.Children will talk to it. The correct behaviour is friendly and harmless.
Intoxicated guestNo special detection — unreliable and intrusive. Instead: the generic T3 confirmation, spend caps and quiet-hours rules already bound the damage.Resist the temptation to build state-of-guest inference. It is invasive, inaccurate, and the generic controls cover the actual risk.
Guest reports another guest (noise, harassment)T4 escalation with context to the duty manager. The agent takes no action itself and does not disclose anything about the other room.Anything affecting another guest is a human decision, always.
Decision D26 — Emergency positioning

Woohoo is never marketed, labelled, described in onboarding, or spoken of by the assistant itself as a way to reach emergency services. In-room collateral must say so. The device says so at the moment it matters. This constrains marketing copy and it should — the alternative is a guest who reasonably believed help was coming. Review this position with counsel in every jurisdiction you deploy in, and treat the property's welfare and emergency protocols as a go-live gate rather than documentation.

Test the kill switches on a schedule

An untested kill switch is a comment in a config file. Exercise each one against the staging fleet quarterly and record the propagation time. During your first serious incident you will not have time to discover that the capability kill only takes effect on the next container restart.
