Part IContext & Executive Summary

1. What Woohoo is, and what breaks today

Woohoo is an in-room voice assistant for hotels. A guest says “Hello Voice Genie” and then asks for something — dim the lights, set the temperature, send housekeeping, order a club sandwich, when is checkout, what's the Wi-Fi password. The device is an Android hub with a screen (com.sb.woohoo), deployed one per guest room, and it fronts whichever building-automation system that particular property runs — Honeywell INNCOM, Interel, or another — plus the hotel's service and F&B operations.

The V1 system is a Dialogflow application. The device performs wake-word detection locally with the Sensory TrulyHandsfree SDK, opens a gRPC stream to Google for speech recognition, receives a matched intent with parameters, and the backend maps that intent onto an API call. Text-to-speech is synthesised on the device using AWS Polly. There is a socket.io channel to the backend for push, Twilio for video calling, Spotify for music, and QR-code enrolment for device provisioning.

That design has four structural problems, and they are the reason V2 exists.

1.1 Intent matching cannot represent what guests actually say

Dialogflow's model is: one utterance → one intent → a fixed parameter set → one action. Guests do not speak that way. “It's freezing in here and can you get someone to look at the shower, it's dripping” is two intents, one of which is a service ticket with a free-text description that no entity extractor was designed to produce. “Make it a bit warmer” requires reading the current setpoint before deciding the target — Dialogflow has no notion of reading state before acting. “Same as yesterday” requires memory. Every one of these becomes a fallback intent, and fallback rate is the single number that determines whether guests keep using the device after day one.

1.2 Every new hotel is an integration project, not a configuration change

Because intents are wired to concrete API calls, a property running Interel needs a different intent-to-action mapping than one running INNCOM, and a property without motorised curtains needs the curtain intents disabled. In V1 that difference lives in code and in branching. This is the reason onboarding a property takes weeks. It is also the reason the system cannot be sold as a product with a price per room — the marginal cost of a customer is engineering time.

1.3 The device holds credentials and makes cloud decisions

The V1 device ships with google-services.json, a Google service-account auth path (google-auth-library-oauth2-http), and AWS Polly SDK credentials. A device physically stolen from a hotel room — which happens — is a credential compromise, and the credential is not scoped to that room. This is the finding that will fail the first serious hotel-chain security review.

1.4 There is no audit trail of why the system did something

When a guest complains that the lights turned off during their shower, or that a $180 room-service order appeared on their folio, V1 can show that an API was called. It cannot show what was heard, what was inferred, what state was read, what was decided and on whose authority. For an agentic system that takes physical actions and spends money, that trail is not optional — it is the product's licence to operate.

The reframing that matters most

V1 asked “which of my known intents is this?” V2 asks “what does this guest want, what am I permitted to do about it in this room, and what is the current state of the world?” The second question is answerable by a model. The first never was.

But the corollary is the whole reason this document is long: once the system can decide, everything the system is not allowed to decide must be enforced outside the model. Roughly two-thirds of this architecture is that enforcement.

3. Executive summary of the target design

Woohoo V2 is a multi-tenant, event-backed agentic platform with a thin edge, a governed tool plane, and a policy layer that sits between the model's intent and the physical world.

3.1 The shape in one paragraph

The device does wake-word detection, voice activity detection, acoustic echo cancellation and endpointing locally, then streams Opus audio over a single authenticated WebSocket to a Device Gateway. The gateway terminates device identity, resolves device_id → tenant / property / room, and hands the session to a Session Orchestrator that owns the turn. The orchestrator streams audio to a cloud ASR provider, and the resulting transcript enters a three-lane router: a deterministic fast lane for the ~60% of utterances that are high-frequency and unambiguous, an agentic lane on Gemini for everything else, and a clarification lane when confidence is low. The agent reasons over a capability-shaped tool surface served by an internal MCP Gateway, which fans out to the property catalogue, device state, service/ticketing, F&B, PMS and knowledge MCP servers. Every tool call the agent proposes passes through a Policy Decision Point that checks tenancy scope, risk tier, quiet hours, spend limits and consent before it is allowed to execute. Execution reaches physical devices through a per-vendor Automation Adapter, which in most properties runs partly on an on-premise Edge Gateway because INNCOM and Interel are LAN-resident systems. The spoken reply is synthesised by streaming TTS and returned over the same WebSocket. Every step emits a span into a per-turn trace and an immutable record into the audit store.

5. Principles that drive the design

P1 — The model proposes, the platform disposesGemini never executes. It emits a proposed tool call; the Policy Decision Point authorises it; the executor performs it. Every constraint that must hold is code, not prose in a prompt. If a guest could talk the model into it, it was never a control.
P2 — Scope is ambient, never arguedThe agent is never asked which room to act on and cannot supply one. Tenant, property and room are derived from the authenticated device identity and injected into every tool call server-side. A tool call for a room the device is not in is structurally impossible.
P3 — Latency is a feature, not a metricA voice assistant that answers in three seconds is perceived as broken regardless of accuracy. Every design choice is evaluated against the latency budget first. This is why the fast lane exists and why the device speaks an acknowledgement before the answer is ready.
P4 — Vendor differences stop at the adapterThe agent knows about “a thermostat in the bedroom zone with a setpoint range”. It never knows about INNCOM or Interel. Every vendor-specific fact lives in an adapter and a per-property capability manifest.
P5 — A new property is dataOnboarding a hotel must be: load a property config, load a room/device inventory, deploy an edge gateway, run a conformance suite. If it requires a code change, the abstraction failed and the abstraction gets fixed.
P6 — Store the decision, not the personThe system retains enough to reconstruct why it acted — redacted transcript, context digest, tool calls, policy verdicts — and as little as possible about who the guest was. Raw audio is never written to disk anywhere.
P7 — Degrade in defined stepsGemini down, ASR down, internet down, BMS down are four different failures with four defined behaviours, ending in local-only automation that still turns the lights on. The device never becomes a brick with a logo.
P8 — Everything on the guest path is tracedOne trace ID from the wake word to the actuation acknowledgement, spanning device, gateway, ASR, agent, MCP, adapter and vendor API. If it is not traced, it cannot be debugged at 3 a.m. across 500 properties.
The single most important principle

P1. Everything else is engineering. P1 is the difference between a product a hotel chain will install in 40,000 rooms and a demo that gets pulled after the first incident. An LLM in the loop of physical actuation and guest billing is only acceptable if the set of things it can cause is bounded by something that does not reason.
