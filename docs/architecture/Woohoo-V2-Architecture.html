Front MatterHow to read this document

This document is the complete target architecture for Woohoo V2 — the second generation of the in-room hospitality voice assistant, rebuilt around an agentic core. It is written to be reviewed and then executed against: every significant choice is stated as an explicit decision with the reasoning and the rejected alternatives beside it, so a reviewer can disagree with a specific line rather than the whole design.

Part IContext & Executive Summary

1. What Woohoo is, and what breaks today

Woohoo is an in-room voice assistant for hotels. A guest says “Hello Voice Genie” and then asks for something — dim the lights, set the temperature, send housekeeping, order a club sandwich, when is checkout, what's the Wi-Fi password. The device is an Android hub with a screen (com.sb.woohoo), deployed one per guest room, and it fronts whichever building-automation system that particular property runs — Honeywell INNCOM, Interel, or another — plus the hotel's service and F&B operations.

The V1 system is a Dialogflow application. The device performs wake-word detection locally with the Sensory TrulyHandsfree SDK, opens a gRPC stream to Google for speech recognition, receives a matched intent with parameters, and the backend maps that intent onto an API call. Text-to-speech is synthesised on the device using AWS Polly. There is a socket.io channel to the backend for push, Twilio for video calling, Spotify for music, and QR-code enrolment for device provisioning.

That design has four structural problems, and they are the reason V2 exists.

1.1 Intent matching cannot represent what guests actually say

Dialogflow's model is: one utterance → one intent → a fixed parameter set → one action. Guests do not speak that way. “It's freezing in here and can you get someone to look at the shower, it's dripping” is two intents, one of which is a service ticket with a free-text description that no entity extractor was designed to produce. “Make it a bit warmer” requires reading the current setpoint before deciding the target — Dialogflow has no notion of reading state before acting. “Same as yesterday” requires memory. Every one of these becomes a fallback intent, and fallback rate is the single number that determines whether guests keep using the device after day one.

1.2 Every new hotel is an integration project, not a configuration change

Because intents are wired to concrete API calls, a property running Interel needs a different intent-to-action mapping than one running INNCOM, and a property without motorised curtains needs the curtain intents disabled. In V1 that difference lives in code and in branching. This is the reason onboarding a property takes weeks. It is also the reason the system cannot be sold as a product with a price per room — the marginal cost of a customer is engineering time.

1.3 The device holds credentials and makes cloud decisions

The V1 device ships with google-services.json, a Google service-account auth path (google-auth-library-oauth2-http), and AWS Polly SDK credentials. A device physically stolen from a hotel room — which happens — is a credential compromise, and the credential is not scoped to that room. This is the finding that will fail the first serious hotel-chain security review.

1.4 There is no audit trail of why the system did something

When a guest complains that the lights turned off during their shower, or that a $180 room-service order appeared on their folio, V1 can show that an API was called. It cannot show what was heard, what was inferred, what state was read, what was decided and on whose authority. For an agentic system that takes physical actions and spends money, that trail is not optional — it is the product's licence to operate.

The reframing that matters most

V1 asked “which of my known intents is this?” V2 asks “what does this guest want, what am I permitted to do about it in this room, and what is the current state of the world?” The second question is answerable by a model. The first never was.

But the corollary is the whole reason this document is long: once the system can decide, everything the system is not allowed to decide must be enforced outside the model. Roughly two-thirds of this architecture is that enforcement.

3. Executive summary of the target design

Woohoo V2 is a multi-tenant, event-backed agentic platform with a thin edge, a governed tool plane, and a policy layer that sits between the model's intent and the physical world.

3.1 The shape in one paragraph

The device does wake-word detection, voice activity detection, acoustic echo cancellation and endpointing locally, then streams Opus audio over a single authenticated WebSocket to a Device Gateway. The gateway terminates device identity, resolves device_id → tenant / property / room, and hands the session to a Session Orchestrator that owns the turn. The orchestrator streams audio to a cloud ASR provider, and the resulting transcript enters a three-lane router: a deterministic fast lane for the ~60% of utterances that are high-frequency and unambiguous, an agentic lane on Gemini for everything else, and a clarification lane when confidence is low. The agent reasons over a capability-shaped tool surface served by an internal MCP Gateway, which fans out to the property catalogue, device state, service/ticketing, F&B, PMS and knowledge MCP servers. Every tool call the agent proposes passes through a Policy Decision Point that checks tenancy scope, risk tier, quiet hours, spend limits and consent before it is allowed to execute. Execution reaches physical devices through a per-vendor Automation Adapter, which in most properties runs partly on an on-premise Edge Gateway because INNCOM and Interel are LAN-resident systems. The spoken reply is synthesised by streaming TTS and returned over the same WebSocket. Every step emits a span into a per-turn trace and an immutable record into the audit store.

5. Principles that drive the design

P1 — The model proposes, the platform disposesGemini never executes. It emits a proposed tool call; the Policy Decision Point authorises it; the executor performs it. Every constraint that must hold is code, not prose in a prompt. If a guest could talk the model into it, it was never a control.
P2 — Scope is ambient, never arguedThe agent is never asked which room to act on and cannot supply one. Tenant, property and room are derived from the authenticated device identity and injected into every tool call server-side. A tool call for a room the device is not in is structurally impossible.
P3 — Latency is a feature, not a metricA voice assistant that answers in three seconds is perceived as broken regardless of accuracy. Every design choice is evaluated against the latency budget first. This is why the fast lane exists and why the device speaks an acknowledgement before the answer is ready.
P4 — Vendor differences stop at the adapterThe agent knows about “a thermostat in the bedroom zone with a setpoint range”. It never knows about INNCOM or Interel. Every vendor-specific fact lives in an adapter and a per-property capability manifest.
P5 — A new property is dataOnboarding a hotel must be: load a property config, load a room/device inventory, deploy an edge gateway, run a conformance suite. If it requires a code change, the abstraction failed and the abstraction gets fixed.
P6 — Store the decision, not the personThe system retains enough to reconstruct why it acted — redacted transcript, context digest, tool calls, policy verdicts — and as little as possible about who the guest was. Raw audio is never written to disk anywhere.
P7 — Degrade in defined stepsGemini down, ASR down, internet down, BMS down are four different failures with four defined behaviours, ending in local-only automation that still turns the lights on. The device never becomes a brick with a logo.
P8 — Everything on the guest path is tracedOne trace ID from the wake word to the actuation acknowledgement, spanning device, gateway, ASR, agent, MCP, adapter and vendor API. If it is not traced, it cannot be debugged at 3 a.m. across 500 properties.
The single most important principle

P1. Everything else is engineering. P1 is the difference between a product a hotel chain will install in 40,000 rooms and a demo that gets pulled after the first incident. An LLM in the loop of physical actuation and guest billing is only acceptable if the set of things it can cause is bounded by something that does not reason.

Part IIIService Decomposition

10. Modular monolith vs microservices — the honest answer

You asked whether this should be modular, whether it should be microservices, and which components must be split. The honest answer has three parts, and the middle one is the one most teams get wrong.

10.1 It must be modular. That is not the same as distributed.

Modularity is non-negotiable here, because the whole product thesis is that a new hotel is configuration rather than code. That requires hard internal boundaries: the agent must not be able to reach into the INNCOM adapter, the F&B service must not read the property catalogue's tables directly, and vendor knowledge must be physically incapable of leaking into the reasoning layer. But every one of those boundaries can be enforced by a module system, a package structure and a lint rule — they do not require a network hop.

10.2 Most of it should not be separate services at Phase 1.

Splitting a system into microservices buys you three things: independent scaling, independent deployment, and failure isolation. It costs you distributed transactions, network failure modes between every pair of components, N× observability plumbing, N× CI pipelines, and — the one that actually kills small teams — the inability to change an interface without a coordinated multi-repo release.

At Phase 1 you have one pilot property and a handful of engineers. The scaling asymmetries that justify a split do not exist yet, and the interfaces are going to change weekly because nobody has yet learned what the agent actually needs from the catalogue. Splitting now means paying the full cost of distribution to buy benefits you cannot use.

10.3 But four things must be separate from day one, for reasons that are not about scale.

Decision D13 — Service granularity

Phase 1 ships five deployable units: (1) woohoo-core, a modular monolith containing the orchestrator, router, agent runtime, MCP gateway and all domain services; (2) device-gateway; (3) policy-service; (4) one automation-adapter-* per vendor; (5) edge-gateway (ships to properties). Everything inside woohoo-core communicates through explicit in-process interfaces that are shaped like network calls — typed request/response, no shared mutable state, no cross-module database access — so that promoting any module to a service later is a transport change, not a redesign.

Split triggers — the rule that keeps this honest

A module is promoted to a service when one of these is measurably true, and never because it feels cleaner:

  • Scaling asymmetry: the module's resource curve diverges >3× from its host (e.g. device-state write volume forcing the whole core to scale out).
  • Deploy contention: two teams block each other more than twice a week, or a release cadence conflict emerges (prompt changes daily vs domain code weekly).
  • Blast radius: the module can exhaust a shared resource — thread pool, connection pool, memory — and take the host down. This is the PMS-bridge and automation-adapter case.
  • Security boundary: the module starts handling untrusted third-party code or data (customer-supplied MCP servers).
  • Compliance boundary: the module's data must live in a different jurisdiction or under a different key than its host.

Write the trigger into the module's README when you create it. Review the list quarterly. This turns “should we split?” from an architecture debate into a metric lookup.

13. Synchronous vs event-driven boundaries

Getting this wrong is the most common way agentic systems become unreliable: teams make the guest-facing path asynchronous for elegance, and then cannot tell the guest whether their request worked.

FlowModeReasoning
Device → Gateway → Orchestrator → ASR → Router → AgentSynchronous / streamingThe guest is standing there. Every millisecond is visible. No queues on this path, ever.
Agent → PDP → MCP Gateway → domain serviceSynchronousThe agent needs the result to compose its reply. A queue here means the agent must speculate about outcomes, which is exactly the hallucination failure mode.
Automation command → adapter → edge → BMSSynchronous with a hard 2.5 s budget, then async continuationMost BMS writes ack in 150–800 ms. If it exceeds budget, the agent says “I've asked for that — give it a moment” and the confirmation arrives later as a screen update and, optionally, a follow-up utterance. Ticket created → staff notificationAsync (event)The guest does not need to wait for a housekeeper's tablet to buzz. Durable delivery matters more than latency.

Analytics / quality metricsAsync, sampledFirehose to S3, batch aggregate. Never on the hot path.
The rule

If the guest is waiting for the answer, it is synchronous. If the guest has already been told, it is asynchronous. The dividing line is the moment the agent finishes speaking, and it is the responsibility of the Session Orchestrator to know which side of that line every operation is on.

Decision D1 — STT placement

Revisit trigger: re-evaluate full on-device ASR when (a) a chain contractually requires audio never to leave the property, or (b) monthly ASR spend exceeds the amortised BOM delta of a better SoC across the fleet — whichever comes first. Keep the AsrProvider interface clean so that day is a swap, not a rewrite.

15.4 The hybrid variant worth keeping in your pocket

There is a third placement nobody asks about and it fits this product unusually well: ASR on the property's Edge Gateway. Audio leaves the room but never leaves the building. A single edge appliance with a modest GPU or a capable CPU can serve a few hundred rooms at realistic concurrency, because hotel voice traffic is sparse and bursty. This gives the privacy story of on-device (audio stays on-premises — a much easier conversation with a hotel's legal team), the per-property vocabulary biasing of cloud, zero per-minute fees, and WAN-outage resilience. What it costs is edge hardware, fleet-wide model management, and accuracy somewhat below the best cloud models.

Recommendation on edge ASR

Do not build it now — it is a distraction from proving the agent. But design the Edge Gateway with enough headroom to host it later (spec the appliance with an upgrade path), and keep AsrProvider implementable at the edge. This becomes your answer when a European or Gulf chain says “guest audio may not leave our premises” — and one of them will.

15.5 The offline command grammar

A fixed, on-device, ~25-phrase recogniser (the same engine family as the wake word handles this well) covering only the actions the device can perform through its local fallback path: lights on/off/dim, temperature up/down, DND on/off, curtains, TV power, and “call the front desk”. When the WAN is down, the device announces the limitation once (“I'm offline right now — I can still do lights, temperature and do-not-disturb”) and operates on this grammar against the Edge Gateway's local rules. Everything else gets a clear refusal and a pointer to the room phone.

17.1 The phrase cache — the highest-value optimisation in the audio path

A large fraction of what the assistant says is drawn from a small set of phrases: acknowledgements (“Sure, one moment”), confirmations (“Done”, “I've set it to 23 degrees”), clarifications (“Which room would you like that in?”), errors, and greetings. These should be pre-synthesised per property voice per language and cached as Opus on the device itself, not fetched per turn.

  • Latency: the acknowledgement plays in <20 ms instead of ~300 ms — and it is the acknowledgement, not the answer, that determines whether the device feels fast.
  • Cost: plausibly 30–45% of TTS characters eliminated.
  • Resilience: the device can still speak when the TTS vendor is down.

Implementation: a versioned phrase pack per (property_voice, language), pushed to devices on provisioning and on voice-config change, with numeric slot substitution handled by a small set of pre-synthesised number fragments for the most common cases (temperatures 16–30, times, small integers).

20.4 Why perceived latency is the only number that matters

The agentic lane's p95 of 4.3 seconds would be a product-killing figure if the guest experienced it as silence. They do not, because the orchestrator emits a filled pause from the device's cached phrase pack the moment the router selects the agentic lane — before the LLM has even responded. The guest hears “Sure, one moment—” at ~600 ms and then the substantive answer flows in behind it.

This is not a trick; it is how humans handle the same problem. Three rules make it work:

  • Vary the phrase. Rotate through 6–8 acknowledgements per language. A device that says exactly the same three words every time sounds broken within a day.
  • Only fill when you will be slow. Fast-lane turns must never get a filled pause — it makes a 600 ms interaction feel slower, not faster.
  • Never acknowledge an outcome you have not achieved. “One moment” is honest; “Done!” before the BMS has acked is a lie the guest will catch when the lights do not change.

23.1 The distribution argument

Hotel voice traffic is extraordinarily head-heavy. Across deployed in-room assistants the top ~20 utterance families — lights, temperature, DND, curtains, TV, checkout time, Wi-Fi password, housekeeping, towels, wake-up call — account for the majority of all traffic, and they are phrased in a narrow range of ways. Paying full agentic reasoning for “turn off the lights” is spending 800 ms and a Gemini call to answer a question a 50-line matcher answers in 4 ms with higher reliability.

The counter-argument — that a fast path is technical debt that will rot — is real, and it is why the fast path in this design is generated and validated by the eval harness rather than hand-maintained (§24.3). If a fast-path rule ever disagrees with what the agent would have done, that is a test failure, and the rule is removed.

Decision D7 — Three-lane router

Every turn is classified into exactly one of three lanes by a deterministic classifier that costs no LLM call:

  • Fast lane — high-confidence match against a curated grammar of top intents, with all slots filled and no ambiguity. Executes directly through the PDP. Target: 55–65% of turns, p50 under 600 ms.
  • Agentic lane — everything else. Full Gemini reasoning over the capability tool surface. Target: 30–40% of turns.
  • Clarify lane — ASR confidence below threshold, or a known-ambiguous reference with no session context to resolve it. Emits a targeted clarifying question without an LLM call where possible. Target: <8% of turns.

24.1 Fast lane escalation

The fast lane must be able to admit defeat. If the matched action's PDP verdict is anything other than ALLOW, or the tool execution returns an error, or the resolved entity is ambiguous, the turn escalates to the agentic lane rather than failing. The guest never learns which lane served them; they only notice that some answers arrive faster.

24.2 What the fast lane may never do

  • Anything at risk tier T3 or above (§44). Money and irreversible actions always get full reasoning plus explicit confirmation.
  • Anything requiring a state read to decide the target value (“a bit warmer”) — unless the state is already in the pre-fetched snapshot and the delta rule is unambiguous.
  • Anything with a free-text field. Free text means judgement; judgement means the agent.
  • Anything when the session has a pending clarification.

24.3 Keeping the fast lane honest

Five percent of fast-lane turns are asynchronously replayed through the agentic lane. Where the agent would have chosen a different action, the disagreement is recorded. A rule whose disagreement rate exceeds 2% is automatically flagged and, if not fixed within a release cycle, disabled. This turns the fast path from accumulating debt into a continuously validated cache of the agent's own behaviour — which is exactly what it should be.

Context caching: the system prompt, tool schemas and property-invariant context are stable across turns and across guests in the same property. Cache them. At scale this is a large fraction of input tokens and it also cuts time-to-first-token.

26.1 Rules for context assembly

  • Layers 0–2 are cacheable and must be byte-stable across turns. Any per-turn variation in them destroys the cache hit and costs both money and time-to-first-token. Do not put a timestamp in Layer 0.
  • Layer 3 is where the pre-fetched state lands. Its assembly must be non-blocking — if the state read has not returned within its budget, the layer is assembled without it and the model is told state is unavailable rather than the turn being delayed.
  • Layer 5 is never concatenated into Layers 0–4. The separation is structural, and it is the primary defence against prompt injection.
  • Nothing in any layer is a security control. If a rule in Layer 0 matters, there is a corresponding enforcement in the PDP. The prompt exists to make the model behave well, not to make it safe.

27.2 Why pre-fetch matters more than it looks

In a naive implementation, “make it warmer” costs: LLM call (→ proposes get_state), tool round-trip, second LLM call (→ proposes set_temperature), tool round-trip. That is two LLM calls and two tool round-trips — roughly 1.6 s of avoidable serial latency and double the token cost. With the state snapshot already in Layer 3, it is one LLM call and one tool round-trip. Across the fleet this is the difference between a viable and an unviable unit cost, and it is why §27 step 1 begins before the guest has finished speaking.

28.1 Anaphora and disambiguation

“Turn it off”, “make it cooler”, “the other one”, “same as yesterday” — these are the utterances V1 could not handle, and getting them right is most of the perceived intelligence gain of V2.

  • Last-referenced entity is tracked explicitly in the conversation layer (entity type, ID, label, turn index) rather than left for the model to infer from history. Explicit beats implicit for anything that determines which physical device gets actuated.
  • Resolution order: (1) explicit reference in the utterance; (2) last-referenced entity if within 2 turns; (3) if exactly one device of the plausible type exists in the room, use it; (4) otherwise ask.
  • Never guess between two physical devices. A wrong guess on “turn off the light” in a suite with five zones is a bad experience; a wrong guess that turns off a light the guest was reading by is worse than asking. The clarify lane exists for this.
  • Relative changes require state. “Warmer” with no known current setpoint is a clarification, not a guess. The pre-fetched snapshot means this is almost always available.

29. Deterministic degraded mode

Gemini will be unavailable, rate-limited or slow at some point. What happens then is a product decision, and the default — an error message — is the wrong one.

 LEVEL 0 · NORMAL          Fast lane + agentic lane + clarify lane. Full capability.

 LEVEL 1 · LLM SLOW        Trigger: p95 LLM latency > 2.5s over a 60s window.
                           Action: cap thinking budget to zero, drop to Flash-Lite for slot filling,
                           widen fast-lane matching thresholds, always emit the filled pause.

                           still useful. THIS IS THE MOST IMPORTANT LEVEL TO GET RIGHT — it is the
                           difference between a degraded product and a broken one.

                           Action: on-screen touch UI on the device takes over — the screen becomes
                           the interface. Voice announces the switch once. All automation and service
                           requests remain available by touch.

 LEVEL 4 · WAN DOWN        Trigger: device cannot reach cloud.
                           Action: on-device grammar (~25 phrases) → LAN → Edge Gateway → BMS.
                           Lights, climate, DND, curtains, TV still work. Service requests are queued
                           locally and flushed on reconnect, and the guest is TOLD they are queued.
                           Screen shows an offline indicator.

                           A honest "I can't reach the room systems right now, please use the phone"
                           beats silence or a lie. Health alert fires to ops.
The degraded-mode principle

At every level the assistant says what it can still do, rather than what it cannot. “I can help with lights, temperature and do-not-disturb right now” keeps the guest using the product; “Sorry, I'm having trouble” teaches them to stop trying. The set of capabilities available at each level is configuration, so it can be tuned per property without a release.

30. Why an MCP gateway is mandatory

You already expose hotel, room, device and service data as MCP servers. The instinct is to point the agent at them directly — that is what MCP is for. For a single-tenant developer tool, that instinct is right. For a multi-tenant system that actuates physical devices in strangers' bedrooms, it is wrong, and the reasons are worth being precise about.

The gateway is the tool plane's control point — registry, filter, scope injector, sanitiser, cache, circuit breaker and audit point — and it is where the “the model proposes, the platform disposes” principle is made mechanical.

31.1 Should vendor adapters be MCP servers?

No. This is worth stating plainly because it is a tempting symmetry. MCP is a protocol for exposing capabilities to a model. The automation adapters must never be visible to the model — the entire point of principle P4 is that the agent reasons about “a thermostat with a setpoint” and has no concept of INNCOM. If inncom-adapter were an MCP server, its vendor-shaped tools would leak into the model's world and the abstraction would be dead within two sprints.

The adapters sit behind the Device State MCP server, which presents a single vendor-neutral surface. Adding Schneider or Lutron support means writing an adapter and a capability mapping. The model's tool list does not change — and the prompt, the evals and the fast-lane grammar all keep working untouched.

33.1 The three levels

  1. Capability — an abstract, vendor-neutral ability with a typed contract: climate.setpoint with a range and unit; curtains.position with 0–100; curtains.open_close as binary. Capabilities are defined once, globally, and versioned.
  2. Capability manifest — per room (usually per room type, with per-room overrides), declaring which capabilities exist, which zones they apply to, what the bounds are, and which driver serves them. This is data, authored during onboarding, versioned, and diffable.

Decision D10 — Capability model

The tool surface presented to the model is generated from the room's capability manifest at context-assembly time. A capability the room does not have produces no tool, so the model cannot propose it, so no runtime check is needed and no apology is ever generated for an action that was never possible. Graceful degradation between capability levels (position control vs binary open/close) is handled in the adapter, not by the model.

The corollary: the manifest is a first-class product artefact. It needs an authoring tool, a validation schema, a diff view, a version history and a conformance test suite that can be run against a real property before go-live. Budget for this properly — it is the thing that determines whether onboarding takes five days or five weeks.

34.3 Idempotency and retry

  • Every mutating tool call carries an idempotency key derived from (turn_id, tool, canonical_args). Replaying the same key returns the original result rather than acting twice.
  • Retries are only automatic for tier T0–T1 (read and reversible-physical). T2 and above are never silently retried — a duplicate maintenance ticket is annoying, a duplicate $200 room-service order is a chargeback.
  • Retry budget: 2 attempts, 150 ms and 400 ms, jittered, and only within the turn's wall-clock budget.
  • Circuit breaker per (property, vendor): 5 failures in 30 s opens it for 60 s. While open, the capability is reported as TEMPORARILY_UNREACHABLE and the agent offers the staff path. One hotel's dead head-end must never consume the adapter's capacity for every other property.

Two modelling decisions worth defending

The voice device is not the room, and is bound to it revocably. The capability manifest attaches to room type, not room. A 300-room property has perhaps eight room types. Authoring eight manifests with a handful of per-room overrides is a day's work; authoring 300 is a project. This single choice is most of the difference between five-day and five-week onboarding.

37. Device state: cache, twin and truth

State consistency is where in-room automation systems quietly break. The BMS is the source of truth, but reading it on every turn is too slow and too fragile.

   TRUTH                      SHADOW                        CACHE                    AGENT

   Freshness contract:
     • fresh   < 10s   → agent uses it silently
     • stale   10–120s → agent uses it but the adapter issues a verify-read after any write
     • expired > 120s  → device-state service forces a synchronous read before answering;
                         if that read fails, the tool returns UNKNOWN and the agent says so
                         ("I'm not sure what it's set to right now — shall I set it to 22?")

   Write path:   agent → PDP → device-state.set → adapter → edge → BMS

                 If no confirmation within 2.5s: agent says "I've asked for that" (not "done"),

Never say “done” on an unconfirmed write

The most damaging failure mode in a voice automation product is the confident false confirmation. The guest hears “I've turned off the lights”, the lights stay on, and the product is dead to that guest. The state machine above exists entirely to make the assistant's confidence proportional to its evidence — “done” when verified, “I've asked for that” when pending, “I couldn't reach the room system” when failed. Encode this in the response templates so it cannot be forgotten.

40.1 Why it is not optional

Decision D12 — The bulk-operation prohibition

“Turn off all the lights in the hotel” is not defended against by a policy rule that rejects it. It is defended against by there being no tool that can express it. Every guest-plane tool operates on exactly one room, and that room is not a parameter. This is worth more than any amount of prompt engineering, and it is the design property to protect hardest during future feature requests — because someone will eventually ask for “turn on all the lights on floor 3 for the fire drill”, and the answer is that it belongs in the staff plane with human authentication, not in the guest tool surface.

46. Prompt injection defence

The agent reads text it did not author: guest speech, staff-written menus and FAQs, ticket histories, and results from vendor systems. Any of it can carry instructions. The defence is layered, and no single layer is trusted.

 LAYER 1 · STRUCTURAL SEPARATION
   Untrusted content never concatenated into instruction layers. It appears only inside explicit
   fenced blocks with a standing rule that content inside is data, never instruction. Layer 0 of the
   prompt (§26) states this once, stably, so it is part of the cached, immutable system identity.

 LAYER 2 · THE PDP DOES NOT READ THE PROMPT
   * The most important layer. Policy decisions are made from the TurnContext and the proposed tool
   call — structured data — and never from the model's reasoning, its explanation, or anything in the
   conversation. An injection can change what the model PROPOSES. It cannot change what is PERMITTED.
   Whatever the attacker convinces the model of, the action still has to pass a component that never
   read their text.

 LAYER 3 · CONTENT SANITISATION
   Tool results scanned before entering context: instruction-like patterns flagged, control characters
   and prompt delimiters stripped, length capped. Staff-authored content (menus, FAQ) is additionally
   scanned at AUTHORING time in the admin UI — catching it once at write beats catching it every read.

 LAYER 4 · CAPABILITY MINIMISATION
   The model can only propose tools present in this room's surface. There is no shell, no HTTP fetch,
   no file access, no code execution, no ability to call an arbitrary endpoint. The "lethal trifecta"
   — private data + untrusted content + external communication — is broken at the third leg: there is
   no egress channel the agent controls.

 LAYER 5 · OUTPUT GUARD
   Replies scanned before TTS for: other-room identifiers, other guests' names, credentials, internal
   IDs, system-prompt fragments, and length. Violations are replaced with a safe response and logged
   as a security event, not silently dropped.

 LAYER 6 · DETECTION
   policy.denied and guard-violation events feed anomaly detection. A device generating repeated
   denials is flagged; a property showing a spike is escalated. Injection attempts become a signal
   rather than an invisible near-miss.
The honest position on prompt injection

Prompt injection is not solved, and any architecture that claims to prevent it at the model layer is overselling. This design therefore assumes injection will sometimes succeed at the model layer and asks a different question: what is the worst thing a fully compromised model can cause?

With the controls above, the answer is: it can say something embarrassing, and it can perform a T0–T2 action in the caller's own room — adjust that room's lights or temperature, or raise a service request that a human will see. It cannot reach another room, cannot spend money without a separate confirmed turn, cannot exfiltrate data because it has no egress, and cannot touch anything at T4/T5. That is a bounded, survivable worst case, and bounding it is the actual goal.

47. Grounding and hallucination control

  • Property facts come only from tools. The prompt explicitly forbids answering questions about amenities, hours, prices or policies from the model's own knowledge. If property.search_knowledge returns nothing, the answer is “I don't have that — let me connect you to the front desk”, and staff.connect makes that a real action rather than a brush-off.
  • Retrieval returns citations, and the turn record stores which knowledge chunks were used. When a guest complains they were told the wrong thing, you can show exactly what the system read.
  • Never invent a capability. Because the tool surface is generated from the manifest, the model cannot propose a curtain action in a room without curtains. For questions rather than actions, the property profile in Layer 1 lists what the property does not have — explicit negative facts prevent a helpful model from assuming a business hotel has a spa.
  • Never invent an outcome. Confirmations are generated from tool results, not from the model's expectation (§37).
  • Uncertainty is a supported answer. “I'm not sure — shall I ask the front desk?” is measured as a success in the eval suite when it is the correct response. If your metrics only reward answering, you will train the system to guess.

54. Secrets, keys and credentials

  • Nothing in images, nothing in the repository, nothing in environment variables in production. Secrets Manager with rotation; injected at task start; never logged, with a log scrubber as the backstop.
  • Per-property vendor credentials (BMS, PMS) stored individually, scoped individually, rotated individually. Never a shared credential across properties — that turns one hotel's incident into all of them.
  • Private CA for device and edge certificates — AWS Private CA or an equivalent — with documented issuance, revocation and CRL/OCSP distribution. Plan revocation before you need it.
  • Key hierarchy: platform CMK for infrastructure; per-tenant CMK for guest data and audit; per-property data key derivation. Key destruction is a valid erasure mechanism and should be part of the offboarding runbook.
  • LLM and ASR API keys scoped to the minimum, rotated on a schedule, monitored for anomalous spend (an unusual token bill is often the first sign of an incident).

55. The consent problem

This is the hardest non-technical problem in the product, and it deserves to be stated plainly: you are placing a microphone in a private bedroom, and the person in that bedroom did not sign anything. Neither did their children, their visitors, or the housekeeper who enters while it is powered on.

55.1 Why the usual answer does not work

“The guest consented at check-in” is weak. Consent under GDPR must be freely given, specific, informed and unambiguous. A line in the terms accepted at a reception desk while queuing, for a device the guest has not yet seen, in a room they cannot decline without declining the room, satisfies none of those adjectives well. And it says nothing at all about the guest's ten-year-old, or the visitor who stayed for dinner.

55.2 The architecture that makes the problem tractable

The way through is not better consent language. It is building a system that does not need strong consent because it does not do the thing that requires it.

Design propertyWhat it means technicallyWhat it buys legally
Wake-word gating, locallyAudio is processed only in a local ring buffer until the wake word fires. The buffer is discarded otherwise. No audio leaves the device without a wake event.The device is not “recording the room”. It is responding to a deliberate address, which is materially different in both law and guest perception.

Decision D22 — Consent posture

Do not rely on consent as the lawful basis for the core service. Rely on the hotel's performance of the accommodation contract and its legitimate interests for room control and service requests — supported by an architecture that minimises processing to what those bases can carry — and reserve consent for the genuinely optional layers: cross-stay preference memory, personalised greeting by name, and any analytics beyond aggregate operational metrics. Those must be opt-in, separately, and revocable.

Document this in a Legitimate Interests Assessment and a DPIA (§62). The DPIA is not optional here: systematic monitoring in a private space, at scale, with novel technology, meets multiple criteria that make one mandatory in the EU and advisable everywhere.

60. PCI, accessibility, life safety

60.1 PCI DSS — the descoping architecture

Woohoo must never see, transmit, process or store a primary account number. Room-service and amenity charges post to the folio via the PMS; the PMS and the hotel's payment provider own settlement, and they are already in scope for PCI. If a future feature appears to require card capture, the correct answer is a redirect to the hotel's existing payment page or app, never card entry by voice.

Never accept a card number by voice

Beyond PCI scope, consider the physical setting: a guest reading a card number aloud in a hotel room, into a device connected to a hotel network, is a bad idea on its own terms. Make it structurally impossible — no tool accepts a card field, and the redactor blocks card-shaped strings on every path unconditionally.

60.2 Accessibility

  • Voice must never be the only path. Guests who are deaf, hard of hearing, non-verbal, or who have atypical speech must be able to reach every function through the device screen. This is both an obligation (ADA in the US, EN 301 549 in the EU, equivalents elsewhere) and simply correct.
  • Screen output must meet contrast requirements, support text scaling, and pair with the spoken response rather than replacing it.
  • Support slower speech, extended endpointing timeouts and repeat requests as a per-room accessibility mode that staff can enable at check-in.
  • The room phone and the physical wall controls must always remain functional. Woohoo augments the room; it must not become a single point of failure for controlling it.

60.3 Life safety

  • Woohoo must not interfere with, gate, or appear to substitute for fire detection, alarms, emergency lighting or door hardware.
  • Automation must fail safe: if the platform is down, wall switches, thermostats and the room phone all still work.
  • No capability may leave a room in an unsafe state — HVAC off in extreme conditions, all lighting off in a windowless bathroom. Encode these as hard PDP bounds per property.
  • Coordinate with the property's fire and life-safety consultant during onboarding where the device is wall-mounted or shares the automation bus with life-safety equipment.

62.3 Data subject rights for a transient guest

A guest who stayed three nights and asks for their data three months later is genuinely hard to identify — you deliberately did not store their name. The answer is to make that a feature rather than an evasion, and to be able to say precisely:

  • Requests are received by the hotel (controller) and passed to Woohoo with the stay reference.
  • Woohoo resolves stay reference → room → turn records for the stay window, and can produce or delete them.
  • Because raw audio is never retained and transcripts are redacted and expire in 30 days, most requests arriving after that window are answered honestly with “this data no longer exists”, which is a compliant and complete answer, and a much better one than a partial export.
  • Erasure for opted-in cross-stay preferences is a real delete plus, where a chain requires it, per-tenant key destruction.
  • Target: acknowledge in 5 working days, fulfil in 30 days. Build the tooling for this before the first request, because it will arrive during a sales cycle.

70.1 The audit record vs the trace

These are deliberately different artefacts with different lifetimes and different audiences. The trace is for engineers, sampled, retained ~14 days, and optimised for debugging. The audit record is for disputes, incidents and regulators — complete (never sampled), immutable, retained 13 months, and containing the policy verdicts. Do not try to make one serve both purposes: the sampling that makes tracing affordable is exactly what makes an audit trail worthless.

70.2 Cost control on observability

At 12.6 M turns/month, full-fidelity tracing is expensive and mostly useless — you will never look at 99.9% of it. Sample: 100% of errors, 100% of T3+ actions, 100% of policy denials, 100% of escalations, 100% of turns for canary properties, and 1–5% of everything else. Aggregate metrics remain unsampled, because that is what alarms fire on.

Two traps in agent evaluation

LLM-as-judge on safety cases. Use it for fluency and helpfulness rubrics where a wrong grade is cheap. Do not use it as the sole gate on the safety or adversarial suites — the failure modes of the judge correlate with the failure modes of the system under test, so it will confidently pass exactly the cases you most need it to catch. Safety cases need deterministic assertions on the tool call plus periodic human review.

Evaluating the model instead of the system. What matters is not whether Gemini produced good text; it is whether the right tool call was proposed, the right policy verdict was reached, and the right physical outcome occurred. Assert on tool calls and verdicts as structured data. Text assertions are secondary.

73. Red teaming

  • Before every major release: an internal exercise against the staging fleet with a written scope — injection through every content path, cross-scope attempts, confirmation bypass, spend manipulation, emergency-path abuse, and denial of service against a single property.
  • Quarterly: external red team on the agent specifically, not just the infrastructure. Most penetration testers will test your API; brief them explicitly to attack the agent's decision-making, the tool surface and the confirmation flow.
  • Continuously: every policy denial and guard violation from production is triaged; genuine attempts become adversarial suite cases within the week.
  • Bug bounty: worth considering once SOC 2 is in place. Scope it to a dedicated test property, never to live guest rooms.

Sequencing advice

Phases 1 and 2 must run in parallel, and Phase 2 is the one that will slip — hardware, vendor access and firmware always take longer than expected. Start the device and edge work first if you can only start one, because the agentic core can be developed against simulators indefinitely while the device work cannot.

Do not let the pilot property be a flagship. Pick a mid-tier property with a co-operative engineering manager, a modern BMS install, and a GM who will tolerate a bad week. Your first flagship deployment should be your fourth property, not your first.
