Read firstWhat you can build today

There are three interfaces in this product, and they are in very different states of readiness. Knowing which you are building determines whether you can start this week.

InterfaceWhat it isStatusTalks to
Device screen The display on the in-room hub. Server-driven content, rendered by the Android app. Ready The Android app renders screen messages — you specify how
Guest surface A web chat, an in-room tablet UI, a demo console — anything where a guest asks for something. Ready POST /v1/turn — three fields, works today
Staff & admin Housekeeping queues, maintenance tickets, property configuration, escalation handling. Blocked No API exists. Part V is the proposed contract to design against
If you are building staff screens, read this before planning your sprint

There is no staff API and no authentication. The service currently exposes exactly three things: a WebSocket for the device, POST /v1/turn, and GET /health. All device-facing.

The logic behind the staff screens exists and is tested — listing and assigning requests, acknowledging escalations, searching what the assistant did, property configuration, kill switches — but none of it is reachable over HTTP. Part V specifies the contract so you can design and mock against it now; building it is roughly a week once two decisions are made (§24).

The thing that shapes every screen you will design

The assistant proposes; the platform decides

The AI never acts on its own. It suggests an action, and a separate component authorises it. That means a request appearing in a response does not mean it happened, and your UI must reflect the difference.

Every action comes back with a verdict: allowed, refused, needs confirmation, or escalated to a human. A refusal is a normal outcome, not an error state — design it as information, not as a failure.

Part IThe guest surface

1. The one call you need

POST http://localhost:8443/v1/turn
content-type: application/json

{ "deviceId": "d_511a", "transcript": "close the curtains and make it warmer" }
async function sendTurn(deviceId, transcript, asrConfidence = 0.95) {
  const res = await fetch('/v1/turn', {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ deviceId, transcript, asrConfidence }),
  });
  return res.json();
}

Three fields. Note what is absent: no room number, no property, no auth token. Identity comes from deviceId and the service derives everything else. There is nowhere in this API to specify a room, deliberately — which is also why a guest cannot ask about someone else's.

2. Response contract

{

  "speech": "Curtains closed. I've set it to 22.5 degrees.",
  "screen": null,

    { "tool": "curtains.set",            "tier": "T1", "verdict": "ALLOW", "ok": true },

  ]

FieldTypeWhat the UI does with it
speechstringThe answer. Display it, speak it, or both. Always short — capped around 45 words.
screenstring?Present only when the display must carry something the words don't — an order total, an emergency number. Render it whenever present. May contain \n.
awaitingConfirmationbooleanA modal state, not a label. See §6. Getting this wrong charges guests for things they didn't confirm.
escalatedbooleanA human was paged. Surface prominently and persistently. See §7.
degradationLevel0–5Non-zero means reduced capability. See §9.
lanestringDiagnostic. fast / agentic / clarify / confirm / degraded. Useful in a debug view; not for guests.
calls[]arrayWhat was attempted and what policy said. Drives “what changed” affordances.
totalMsnumberServer-side duration. Debug views only.

2.1 Reading calls[] correctly

`verdict` and `ok` are two different questions

verdict asks was it allowed?  ok asks did it work?

A call can be ALLOW with ok: false — policy permitted it and the room system then failed. That is a genuinely different message to the guest than a refusal, and your UI should not collapse the two.

verdictMeansUI treatment
ALLOWAuthorised, and executed if okNormal success. Show what changed.
CONFIRMFrozen, waiting for a spoken yesEnter confirmation state (§6)
DENYPolicy refused itNot an error. Neutral, informative. No red, no alarm icon.
ESCALATEHanded to a humanProminent, persistent (§7)

2.2 HTTP status codes

CodeMeaningUI
200Turn completed — including refusalsRender speech. Do not treat as failure.
400Missing field or bad JSONClient bug
404Unknown or revoked deviceConfiguration problem, not a guest problem
413Body over 16 KBCap input length client-side
500Internal faultHonest error; offer the front desk. Do not auto-retry — it may have half-executed.

6. Confirmation — the critical one

Three rules, and they are not negotiable
  1. Never auto-confirm. Not on timeout, not on ambiguity, not on a "seems fine" heuristic. Only an explicit affirmative from the guest.
  2. Always show the total. The guest is agreeing to a charge on their room bill. The screen is the record they can read and re-read; the spoken sentence is not.
  3. Always offer a way out. A visible cancel, not just "say no".
Suggested layout — confirmation
  ┌────────────────────────────────────────────────┐
  │  Confirm your order                            │
  │                                                │
  │  2 items                                       │
  │  ┌──────────────────────────────────────────┐  │
  │  │            ₹1,240                        │  │  ← largest element
  │  │       charged to your room               │  │     on the screen
  │  └──────────────────────────────────────────┘  │
  │                                                │
  │  [  Yes, place it  ]     [  Cancel  ]          │
  │                                                │
  │  Expires in 1:23                               │  ← optional but honest
  └────────────────────────────────────────────────┘

6.1 The 90-second expiry

The frozen action expires server-side after 90 seconds regardless of what your UI does. A late "yes" is therefore safe — the guest is told it expired and nothing is charged. Mirror the expiry in your UI so the two do not disagree, and clear the state on expiry rather than leaving a stale confirm button.

Why "yes" cannot be misinterpreted

When the guest confirms, the platform executes the exact action it froze — it does not re-read their words. So even if someone said "yes, and make it ten sandwiches", the ten does not happen. Useful to know when designing the copy: the confirm step is a yes/no gate, not a place to amend the order.

7. Escalation — the other critical one

Do not edit, shorten, summarise or translate this wording

Escalation text is a compliance artefact, not copy. It states plainly what the system cannot do — because a guest who believes an ambulance is coming when it is not is the worst outcome this product can produce.

Render speech and screen verbatim. Do not add your own reassurance on top, and do not replace "I'm not able to call them for you" with something softer.

RequirementDetail
PersistentNever auto-dismiss. Requires explicit user action to clear.
ProminentHighest-priority element. It outranks anything else on screen.
Emergency number legibleLarge. It arrives in screen and comes from property config — it is not always 112.
VerbatimNo paraphrasing, no truncation, no ellipsis.
Stays interactiveThe guest can keep talking. Do not lock the interface.

8. Refusals and limits

Refusals are frequent and intentional. Treated as errors, the interface will feel broken when it is working exactly as designed.

Guest asks forWhat happensDesign as
A temperature outside the hotel's bandDENY, R6.out_of_boundsNeutral information
Something their room type doesn't haveNo tool exists; a plain spoken answerNeutral information
Another guest's detailsRefusal — structurally impossible to answerNeutral. Never "access denied" framing
The door unlockedRefusal; no such capability exists at any levelNeutral, with the front desk offered
Too many changes too fastDENY, rate limitGentle, temporary
An order over the spend capDENY, spend ruleNeutral, offer the front desk
Tone

The service already words refusals well — "I can only help with your own room." Your job is not to improve on it but to not wrap it in alarming chrome. No red, no warning triangle, no "Error" heading. It is an answer, not a fault.

9. Degraded and offline

LevelWhat happenedGuest sees
0NormalNothing
1AI slowNothing — handled invisibly
2AI unavailableSimple requests still work; reply names what still works
3Speech unavailableScreen becomes the primary interface
4Internet downLights, temperature, DND still work locally
5Everything downHonest message pointing at the room phone
The pattern to follow throughout

Say what still works, not what is broken. "I can help with lights, temperature and do-not-disturb right now" keeps the guest using the product. "Sorry, I'm having trouble" teaches them to stop trying. The backend already words its degraded replies this way — match it in your own offline and error states.

Part IIIThe device screen

10. How it works

The in-room hub has a display. Its content is decided by the server and arrives as a screen message; its presentation is yours. The device renders, it never decides.

← {"type":"speak",  "text":"I've set it to 22.5 degrees.", "turnId":"turn_…"}
← {"type":"screen", "text":"22.5°C"}

You are designing the screen states; the Android team implements them. Two constraints from the protocol: screen is plain text that may contain \n — never markdown, never HTML — and it is only sent when the display carries something the audio does not.

11. Screen states

  IDLE ──wake word──► LISTENING ──guest stops──► THINKING ──ack──► SPEAKING
    ▲                                                                 │
    │                                                                 │ chargeable
    │                                                                 ▼
    │                                                          CONFIRMING
    │                                                                 │
    └──────────────────────── done / cancelled / expired ─────────────┘

  Cross-cutting: MUTED (hardware switch) · OFFLINE · SERVICE (fatal)
StateMust communicateDesign notes
IDLERoom is ready; device is not listeningAmbient. Time, room number, maybe weather. Should be pleasant to have on a bedside table at 3 a.m. — dim, no motion.
LISTENINGUnambiguously that the mic is liveThe most important honesty signal in the product. Distinct, immediate, impossible to miss.
THINKINGWorking on itMay last 30 ms. Fade in after ~150 ms so fast turns don't flash.
SPEAKINGWhat was said and what changedShow screen if present; otherwise the speak text.
CONFIRMINGThe totalThe amount is the largest element. See §6.
MUTEDMic is off in hardwareUnmistakable and persistent. Guests must be able to trust it at a glance from across the room.
OFFLINEReduced capability + what still worksBadge, not a takeover.
SERVICENeeds staff attentionNeutral. Not the guest's problem to solve.
Two states carry trust, not just information

LISTENING and MUTED are the two that decide whether a guest believes the device isn't spying on them. If either is subtle, ambiguous, or looks similar to a neighbouring state, the product has a credibility problem no amount of privacy policy fixes.

Design them to be readable from the bed, in the dark, without glasses.

12. Latency and the filled pause

There is a mechanism you should design around rather than fight.

guest stops speaking          at    0ms
ack   "Let me sort that—"     at    2ms   ← device speaks HERE
speak "I've set it to 22.5"   at 1846ms

The device says something reassuring within milliseconds, from cached audio, then the real answer arrives up to two seconds later. Measured on the real stack.

Implication for the screenWhat to do
Audio and screen can be ~2 s apartDo not wait for speak to leave IDLE. Enter THINKING when the utterance ends.
Fast turns are genuinely fastA spinner that appears for 39 ms is worse than none. Delay it ~150 ms.
The device is already talking during THINKINGTHINKING should not look like silence — it should look like attentiveness.

Part IVCraft

13. Accessibility

Voice must never be the only path

Guests who are deaf, hard of hearing, non-verbal, or who have atypical speech must be able to reach every function through the screen. This is an obligation under ADA and EN 301 549 — and in an emergency the screen works when speech does not, which is exactly when it matters most.

RequirementDetail
Every spoken reply on screenNot a summary. The same words.
Every function touch-reachableIf it can be asked for, it can be tapped. No voice-only capability.
ContrastWCAG AA minimum; AA-large for anything read from across a room.
Text scalingSupport system scaling. In-room devices are used by older guests without their glasses.
MotionRespect reduced-motion. Nothing that pulses in a dark bedroom.
Touch targets44 pt minimum. Guests are often standing, holding something, half asleep.
Slow-speech modeA per-room setting staff enable at check-in extends how long the device waits before deciding the guest has finished. Surface it in the admin UI (§16).
Never colour aloneEspecially for MUTED and LISTENING.

14. Copy and tone

Most guest-facing wording comes from the server, already toned per property. Your copy is the scaffolding around it: labels, buttons, empty states, errors.

PrincipleDoDon't
Never claim an outcome you don't have"I've asked for that""Done!" before confirmation
Refusals are information"That's not something I can do here.""Error: permission denied"
Say what still works"I can still do lights and temperature.""Service unavailable"
Money is explicit"₹1,240 charged to your room""Confirm order"
No jargon"the front desk""escalate to T2 support"
BriefOne idea per screenParagraphs on a bedside display
Never surface these internals to a guest

lane, tier, ruleId, turnId, verdict, tool names like climate.set_temperature, and degradationLevel as a number.

They are exactly right for a debug view or the staff console. To a guest they are noise, and "T3 CONFIRM R11.confirmation_required" is not a sentence anyone should read on holiday.

15. What never to show

Never displayWhy
Another room's number or any other guest's detailsThe service refuses these structurally, but a UI must not reintroduce them by, say, showing a property-wide feed on a guest surface.
Full card numbers, everThe system blocks them on every path. Never add a field that accepts one — a guest reading a card number aloud in a hotel room is a bad idea on its own terms.
Raw internal errors or stack traces—
Staff names or internal assignment detailOn guest surfaces.
"AI" framing on an emergency screenIn an escalation the guest needs a phone number, not a disclaimer.

This API does not exist yet

16. Screens needed

ScreenWho uses itMust do
Request queueHousekeeping, maintenanceLive list of open requests with room, category, age, SLA countdown. Assign, start, complete. This is the screen someone stares at all shift — it deserves the most attention.
EscalationsDuty manager, front deskUnacknowledged emergencies, loudly. Acknowledge with a name attached. An escalation nobody acknowledges is the worst failure in the system — design the alarm for that case first.

Before designing the request queue, settle one product question

Most hotels already run HotSOS, Quore or Alice, and no hotel wants a second queue for their staff to watch. If we push requests into their existing system, this screen becomes a thin monitoring view rather than a working queue — a very different design.

Worth resolving with sales before investing in it.

17. Proposed API contract

Shapes to design and mock against.

17.1 Requests

GET  /v1/staff/requests?propertyId=&status=open&category=
  → { "requests": [ {
        "id": "sr_ms71…", "roomNumber": "412", "category": "maintenance",
        "description": "shower dripping", "priority": "normal",
        "status": "open", "createdAt": "2026-07-29T23:14:02Z",
        "slaDueAt": "2026-07-29T23:59:02Z",
        "deferred": true, "dispatchAt": "07:00",
        "assignee": null
      } ] }

POST /v1/staff/requests/{id}/assign     { "assignee": "staff_42" }
POST /v1/staff/requests/{id}/status     { "status": "in_progress" | "completed" }

deferred and dispatchAt matter for the UI: a non-urgent request raised at 23:14 is deliberately queued for 07:00 so the guest isn't disturbed. Show that clearly — otherwise staff see an old untouched ticket and think the system is broken.

17.2 Escalations

GET  /v1/staff/escalations?acknowledged=false
  → { "escalations": [ {
        "id": "esc_ms71…", "roomNumber": "412",
        "category": "medical",          // medical | fire | security | welfare | other
        "severity": "critical",
        "summary": "Guest reported chest pain",
        "raisedAt": "2026-07-29T23:14:02Z",
        "requiresAckWithinS": 120,
        "acknowledgedAt": null, "acknowledgedBy": null
      } ] }

POST /v1/staff/escalations/{id}/ack     { "staffId": "staff_42" }

17.3 Rooms and devices

GET  /v1/staff/rooms/{roomId}
  → { "roomNumber": "412", "roomType": "Deluxe King",
      "state": { "zones": [ { "zone":"bedroom",
                              "lighting": { "on": true, "brightness": 70 },
                              "climate":  { "currentC": 24.5, "setpointC": 22.5,
                                            "minC": 18, "maxC": 26 } } ],
                 "dnd": "off", "freshness": "fresh" },
      "openRequests": [ … ], "recentOrders": [ … ],
      "device": { "deviceId":"d_412a", "online": true, "rssi": -58,
                  "firmware": "2.4.1", "lastSeen": "…" } }

freshness is worth surfacing: fresh / stale / unknown. On unknown the room state could not be read — show it as unknown rather than displaying a stale number as current.

17.4 Activity log

GET  /v1/staff/turns?roomId=&from=&to=
  → { "turns": [ {
        "turnId": "turn_ms71…", "at": "…", "roomNumber": "412",
        "transcript": "it's freezing in here",     // redacted
        "response": "I've set it to 22.5 degrees.",
        "outcome": "success", "escalated": false,
        "actions": [ { "tool": "climate.set_temperature", "verdict": "ALLOW",
                       "ruleId": "allow", "result": "applied" } ]
      } ] }

This is the dispute-resolution screen. Design it so a duty manager can answer "why did the room get cold at 2 a.m." in under a minute. Transcripts are redacted and retained ~30 days; action records are kept far longer, so a search may return actions with no transcript — handle that gracefully rather than showing an empty row.

17.5 Configuration and kill switches

GET  /v1/admin/properties/{id}                    // full config
PUT  /v1/admin/properties/{id}/policy             // temp bands, quiet hours, spend caps
PUT  /v1/admin/properties/{id}/room-types/{rtId}  // capability manifest
PUT  /v1/admin/rooms/{roomId}/overrides           // e.g. disable curtains: motor broken

POST /v1/admin/properties/{id}/kill-switch
     { "disabledTools": ["fnb.place_order"] }     // disable one capability
     { "tierCeiling": "T0" }                      // read-only mode
Kill switches are incident tools — design them for a bad night

Someone reaches for these when something is going wrong, possibly at 2 a.m., possibly while a manager is on the phone. Requirements: unmistakable current state, obvious blast radius ("this affects all 300 rooms at Whitefield"), a confirmation step, and an equally obvious way to undo. Never bury them in a settings tab.

18. Live updates

Polling a request queue is the wrong shape — a housekeeping tablet should buzz within seconds. Proposed: Server-Sent Events.

GET /v1/staff/events?propertyId=p_blr_whitefield
  Accept: text/event-stream

event: service_request.created
data: { "id":"sr_…","roomNumber":"412","category":"maintenance","priority":"normal" }

event: escalation.raised
data: { "id":"esc_…","roomNumber":"412","category":"medical","severity":"critical" }

event: device.offline
data: { "deviceId":"d_412a","roomNumber":"412" }

Design for reconnection: SSE drops. On reconnect, refetch the list rather than assuming the stream filled every gap.

19. Permissions model

The staff API will be the only inbound path into the system, so it carries the most scrutiny. Roles shape your navigation, so they are worth agreeing early.

RoleScopeCan
Housekeeping / maintenanceOne propertySee and update requests assigned to their department
Front deskOne propertyAll requests, room view, acknowledge escalations
Duty managerOne propertyEverything above + activity log + kill switches
OpsMany propertiesConfiguration, devices, onboarding
SupportMany, auditedRead-only activity log

Every request will be validated against the caller's property claim server-side. Design as if a user may hold access to several properties: a property switcher is easier to add now than to retrofit.
