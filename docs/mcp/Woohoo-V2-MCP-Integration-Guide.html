The one idea that governs everything in this guide

The agent reasons about capabilities, never about vendors. It knows there is "a thermostat in the bedroom zone with a permitted range". It has never heard of INNCOM, Interel, BACnet objects or KNX group addresses.

Every vendor-specific fact lives in exactly two places: an adapter, and a per-property capability manifest. If vendor vocabulary ever appears above those, the abstraction is broken and adding the next hotel becomes an engineering project again.

Part IMCP

1. What MCP means here

MCP is a protocol for exposing capabilities to a model. In Woohoo it is an internal plane: the agent proposes tool calls, and a gateway executes them. It is not a public API, and no external system calls it.

   AGENT ───► MCP GATEWAY ───┬──► property catalogue      (rooms, devices, manifests)
   proposes    the control   ├──► device state    ───► automation adapter ───► the room
   only        point         ├──► service requests
                             ├──► F&B orders
                             ├──► PMS bridge
                             ├──► knowledge / FAQ
                             ├──► guest preferences
                             └──► notification / escalation

   The agent can NEVER address any of these directly. That single rule is what makes
   tenant scoping mechanical instead of a code-review question.
The gap you need to know about before planning

The gateway currently dispatches through an in-process map of handler functions:

const result = await gateway.execute(scoped, ctx);   // a function call

There is no MCP client, no JSON-RPC, no Streamable HTTP in the codebase. So the MCP servers you already have — hotel, room, device, services — are not connected to this system. The gateway was designed to front them, but today it fronts local functions. §3 is that work.

2. The gateway's six jobs

Understanding these explains why the agent is not simply pointed at your MCP servers directly — which is what MCP is for, and would be right for a single-tenant developer tool.

JobWhat happens without itWhat the gateway does
Scope injectionThe room to act on comes from model output. A model error or an injected instruction can address another guest's room. Nothing structural prevents it.Strips any room/property/tenant field the model produced and injects the real one, derived from the authenticated device.
Per-room filteringEvery hotel sees every tool. A room without curtains gets a curtain tool the model will happily call.Filters the advertised tool set by that room's capability manifest before the agent sees it.
Result sanitisationA menu description edited by a hotel employee becomes a prompt-injection vector.Fences untrusted content and scans it before it enters the model's context.
Error normalisationINNCOM: ERR_0x8004 reaches the model, which either hallucinates an explanation or apologises uselessly.Maps everything into one small vocabulary the model is taught to handle.
CachingThe catalogue is read on every turn and changes weekly — the hottest and most wasteful query in the system.Per-tool TTLs with explicit invalidation.
Uniform auditEach server logs differently, or not at all.One place records every call, its arguments digest, its verdict, latency and outcome.

2.1 Scope injection, concretely

{ // what the model emitted — note the room_id it invented
  "tool": "climate.set_temperature",
  "args": { "zone": "bedroom", "targetC": 23.0, "room_id": "999" }
}

{ // what actually executed
  "tool": "climate.set_temperature",
  "args": { "zone": "bedroom", "targetC": 23.0 },        // room_id STRIPPED
  "scope": {                                          // injected server-side
    "tenantId":   "t_demo_apac",
    "propertyId": "p_blr_whitefield",
    "roomId":     "r_412",
    "deviceId":   "d_412a"
  },
  "idempotencyKey": "sha256(turnId | tool | canonical args)"
}
Stripped, not validated — and the difference matters

Validating a model-supplied room_id against the real one would mean the field exists in the surface. Which means it can be populated. Which means somebody will eventually "temporarily" trust it for a staff feature. Removing the field removes the class of bug.

Design your MCP tools the same way: no tool takes a room, property or tenant identifier. Scope arrives out of band.

3. Connecting your MCP servers

This is the integration work. Everything above the transport already exists — you are implementing one interface.

// services/woohoo-core/src/modules/mcp-gateway.ts
export type ToolHandler = (
  call: ScopedToolCall,   // tool, args, scope, turnId, idempotencyKey
  ctx:  TurnContext,
) => Promise<unknown>;

Today a handler is a local function. To use a real MCP server, it becomes a client call:

/**
 * Bridges one Woohoo tool to a tool on a real MCP server.
 *
 * Everything above this — filtering, policy, audit — is unchanged. The gateway does not
 * care whether a handler is local or remote.
 */
function mcpHandler(client: McpClient, remoteToolName: string): ToolHandler {
  return async (call, ctx) => {
    const res = await client.callTool({
      name: remoteToolName,
      arguments: {
        ...call.args,
        // Scope travels OUT OF BAND, not as tool arguments (see §2.1).
      },
      // Per-call, audience-bound, short-lived. A compromised server must not be able
      // to replay this token against a different server.
      _meta: { woohooScope: call.scope, turnId: call.turnId },
    }, { timeoutMs: 2500 });

    if (res.isError) {
      // Normalise. Raw upstream errors must never reach the model.
      return toolError(
        ToolErrorCode.TemporarilyUnreachable,
        'That system is not responding right now.',
        'Tell the guest you could not complete it and offer the front desk.',
        true,
      );
    }
    return res.content;
  };
}

3.1 What the MCP server must guarantee

RequirementWhy
Honour the scope, don't trust argumentsThe server must resolve which room from the out-of-band scope, and reject or ignore any room identifier in the arguments. This is the single most important requirement.
No cross-tenant reachabilityGiven scope for property A, it must be impossible to read or write property B — even with a crafted argument.
Bounded latencyReturn within ~2.5 s or fail. The turn has an 8-second wall clock and a guest is standing there.
IdempotencyHonour idempotencyKey on mutations. Retries happen; double actuation must not.
Structured errorsDistinguish "not available in this room" from "upstream is down" — they produce different things for the guest to hear.
No side effects on readRead tools are pre-fetched speculatively on most turns, before anyone knows whether they are needed.

3.2 Transport

OptionUse whenNotes
In-processTodayZero latency. Same interface, so promotion later is a config change.

4. What must never be an MCP tool

Automation adapters are not MCP servers, and this is a tempting mistake

The symmetry is appealing: if the catalogue is an MCP server, why not inncom-adapter?

Because MCP exposes capabilities to a model. If the INNCOM adapter were an MCP server, its vendor-shaped tools would appear in the model's world, and within two sprints the agent would be reasoning about object IDs and register writes. The abstraction that makes a new hotel a config change would be dead.

Adapters sit behind the device-state server, which presents one vendor-neutral surface. Adding Schneider or Lutron means writing an adapter and a mapping — the model's tool list, the prompts and the tests all stay untouched.

Never expose as a toolInstead
Anything vendor-shaped — object IDs, registers, group addressesA capability behind an adapter
Anything taking a room, property or tenant parameterAmbient scope
Anything operating on more than one roomStaff plane, human-authenticated, with a cap on rooms per operation
Door locks, safes, microphone activationNothing. No tool exists at any tier, deliberately.
Raw SQL or arbitrary query executionPurpose-shaped read tools
Anything handling a card numberFolio posting via the PMS only

5. The domain model

  TENANT (chain) ──1:*──► PROPERTY (hotel) ──1:*──► ROOM ──*:1──► ROOM_TYPE
                              │                      │               │
                              │                      │               └─► CAPABILITY_MANIFEST
                              │                      │                   (versioned)
                              │                      │
                              │                      ├─► ROOM_OVERRIDE  (may only REMOVE)
                              │                      │
                              │                      └─► vendor_room_id  ← NOT the room number
                              │
                              ├──► EDGE_GATEWAY (1–2 per property)
                              └──► PROPERTY_POLICY (temp bands, quiet hours, spend caps)

  WOOHOO_HUB (the voice device) ──bound to──► ROOM
      · separate entity, revocable, timestamped, re-verifiable
Two modelling decisions worth understanding before you touch the schema

The device is not the room. Modelling the hub as a separate entity with an explicit, timestamped binding is what makes mis-binding detectable. Collapse them — treat device ID as room ID — and a device moved during a refurbishment silently controls the wrong room while the audit log records it as correct. That bug surfaces nowhere unless you build for it.

The manifest attaches to room type, not room. A 300-room property has perhaps eight types. Eight manifests plus a handful of overrides is a day's work; three hundred is a project. This single choice is most of the difference between five-day and five-week onboarding.

6. What the agent needs per turn

Five reads, all fired in parallel while the guest is still speaking. Together they remove an entire tool round-trip — roughly 400–600 ms — from most turns, so their latency is on the critical path.

ReadBudgetCacheReturns
Device resolution<5 ms60 sdeviceId → tenant, property, room, manifest, vendor room ref. Must not cost a DB hit per turn.
Room state<1.2 s10 s freshLighting, climate, curtains, DND per zone, plus a freshness marker
Open requests<300 ms—So the agent doesn't raise a duplicate
Stay context<1.5 s15 minCheckout time, room type, wifi, folio total — tokenised, no guest name unless consented
Preferences<300 ms—Empty unless the guest opted in
Design your reads to be cheap and batched

One room.get_state returning everything beats five per-device reads. Every mutating tool should also return the resulting state, which removes a read-back round trip and lets the agent confirm truthfully rather than optimistically.

7.1 Repository interfaces

Every store sits behind an interface with an in-memory implementation, which is why the whole system runs with no database. Adding Postgres is implementing the same interface.

export interface CatalogRepository {
  getProperty(propertyId: string): Promise<PropertyConfig | undefined>;
  getRoom(roomId: string): Promise<RoomRecord | undefined>;
  getDevice(deviceId: string): Promise<DeviceRecord | undefined>;
  listRooms(propertyId: string): Promise<RoomRecord[]>;
  upsertProperty(cfg: PropertyConfig): Promise<void>;
  upsertRoom(room: RoomRecord): Promise<void>;
  upsertDevice(device: DeviceRecord): Promise<void>;
}
One thing to fix while you are in there

All state is currently held in in-process Maps — sessions, device shadow, pending confirmations, catalogue cache. That means the service runs as exactly one instance: two replicas would each hold different conversation history, and a payment confirmation minted on one could not be redeemed on the other.

Moving these to Postgres and Redis behind the existing interfaces is what unlocks horizontal scaling. It is a prerequisite for production, not an optimisation.

8. Tenant isolation

Row-level security is enabled on every tenant-scoped table. It is a backstop, not the primary control — the primary control is that every query goes through a repository carrying the tenant. RLS is what saves you the day someone forgets.

-- app.tenant_id is set per connection by the repository layer
CREATE POLICY tenant_isolation ON service_request
  USING (tenant_id = current_setting('app.tenant_id', true));
The test to write

For every store: "if a query here forgot its tenant filter, what would happen?" If the answer is "it returns another hotel's data", you need the backstop. Build a CI test that runs representative queries under a tenant-scoped role and asserts zero cross-tenant rows — this is the first control a hotel chain's penetration test will probe.

9. Caching and freshness

Device state is the interesting one. The automation system is the source of truth, but reading it every turn is too slow and too fragile.

   TRUTH                SHADOW                  CACHE              AGENT
   ─────────            ──────────              ──────────         ──────────
   head-end  ──push──►  edge local  ──stream──► cloud state ──►    room.get_state
             ◄─write──  shadow      ◄─command── service

   fresh   (<10s)     → serve from shadow, no read
   stale   (10–120s)  → serve from shadow, but verify-read after any write
   expired (>120s)    → force a synchronous read; if that fails return UNKNOWN
                        and the agent says "I'm not sure what it's set to right now"
                        rather than confidently reporting a stale number

Surface the freshness marker in any read tool you build. An honest "unknown" is far better than a confident stale value — the guest can hear the difference when the room doesn't match.

Why absence beats refusal

A capability the room lacks produces no tool. The model cannot propose it, so no runtime check is needed and no apology is generated for something that was never possible.

The vendor room reference trap

vendorRoomId (e.g. INN-0412) is the automation system's own identifier. 13. The contract

export interface AutomationAdapter {
  readonly vendor: string;

  connect(binding: PropertyBinding): Promise<ConnectionHandle>;
  health(): Promise<{ reachable: boolean; latencyMs: number; lastError?: string }>;

  readRoomState(room: VendorRoomRef): Promise<CapabilityState[]>;
  subscribe(room: VendorRoomRef, cb: (change: StateChange) => void): Unsubscribe;

  /** Capability in, capability out. Vendor vocabulary never escapes this file. */
  applyCapability(
    room: VendorRoomRef,
    op: CapabilityOperation,     // { capability, zone?, value }
    idempotencyKey: string,
  ): Promise<CapabilityResult>;  // { status, observed?, message? }

  /** Run at onboarding and nightly against a designated test room. */
  conformanceSuite(): ConformanceTest[];
}

Six methods. Everything else in the platform is built on them.

14. Writing an adapter

export class InncomAdapter implements AutomationAdapter {
  readonly vendor = 'inncom';

  private objectMap!: ObjectMap;   // per-installation, from config — NOT hardcoded
  private conn!: HeadEndConnection;

  async connect(binding: PropertyBinding) {
    // Credentials come from the secret store, scoped to ONE property.
    // Never a shared credential across properties — that turns one hotel's
    // incident into everyone's.
    const creds = await secrets.get(binding.secretRef!);
    this.objectMap = await loadObjectMap(binding.propertyId);
    this.conn = await HeadEnd.open(creds);
    return { propertyId: binding.propertyId, connectedAt: Date.now(),
             close: () => this.conn.close() };
  }

  async applyCapability(room, op, idempotencyKey) {
    // 1. Idempotency — replays must not actuate twice.
    const prior = this.seen.get(idempotencyKey);
    if (prior) return prior;

    // 2. Translate capability → vendor. THE ONLY PLACE THIS HAPPENS.
    const target = this.objectMap.resolve(room.vendorRoomId, op.capability, op.zone);
    if (!target) {
      return { status: 'rejected',
               message: `No ${op.capability} in room ${room.vendorRoomId}` };
    }

    // 3. Actuate.
    await this.conn.setLevel(target.objectId, encodeValue(op, target));

    // 4. Read back. "Applied" must mean OBSERVED applied (§17).
    const observed = await this.readCapability(room, op.capability, op.zone);
    const result: CapabilityResult = observed
      ? { status: 'applied', observed }
      : { status: 'pending' };

    this.seen.set(idempotencyKey, result);
    return result;
  }
}

15. Capability degradation

Rooms differ in what their hardware can do. The adapter absorbs that, not the model.

case CapabilityId.CurtainsPosition: {
  const requested = clamp(Number(op.value), 0, 100);

  // A binary motor snaps to fully open or fully closed. The model asked for a
  // position and gets a truthful observed value back — it never learns why.
  const binary = this.objectMap.isBinaryCurtain(room.vendorRoomId, op.zone);
  const applied = binary ? (requested >= 50 ? 100 : 0) : requested;

  await this.conn.setLevel(target.objectId, applied);
  return { status: 'applied',
           observed: { capability: op.capability, zone: op.zone,
                       value: applied, available: true } };
}

Return the observed value, not the requested one. The agent confirms from what it observes, so a guest asking for 40% in a binary room hears "curtains closed" — which is true — rather than "set to 40%", which would not be.

16. Failure, retries, circuit breakers

SituationBehaviour
Head-end slowHard 2.5 s budget. Beyond it the result is pending, and the guest is told "I've asked for that" — never "done".
Head-end unreachableReturn an error. The platform normalises it to TEMPORARILY_UNREACHABLE and offers the front desk.
Repeated failuresCircuit breaker per (property, vendor): 5 failures in 30 s opens it for 60 s.
RetryAutomatic only for reads and reversible physical actions. Never for anything creating a commitment.
IdempotencyHonour the key. Retries happen; double actuation must not.
The circuit breaker is the most important resilience control in the system

One hotel's hung head-end must never consume the adapter's capacity for every other property. Without per-property bulkheading, the single most likely production incident is: one flaky BMS takes down voice control for every hotel on the platform.

This is also the reason adapters are separate deployable services rather than modules.

17. Verify-read

Never report success you did not observe

The most damaging failure mode in this product is the confident false confirmation: the guest hears "I've turned off the lights", the lights stay on, and the device is dead to them.

Real systems acknowledge writes that never take effect — the simulator models this deliberately as "silent failure". The only defence is reading the state back.

ReturnWhenGuest hears
appliedRead-back confirms the new value"I've set it to 23 degrees."
pendingAcknowledged but not yet observed"I've asked for that — give it a moment."
rejectedThe system refused it"That's not something I can do here."
throwUnreachable"I can't reach the room systems right now."

Part VOn premises

18. Why the edge gateway exists

Four reasons, and they are not negotiable:

  • INNCOM and Interel head-ends are LAN-resident, typically on an isolated building network with no outbound route and certainly no inbound one.
  • Hotel IT will not open inbound firewall ports for a vendor — and the request alone delays onboarding by months.
  • Round-tripping every light command to a cloud region adds 60–200 ms to an action whose entire budget is under a second.
  • When the property WAN drops — routine — the guest must still be able to turn on the lights. Only something inside the building can deliver that.
  PATH 1 — VOICE (normal turn)      device ═══► cloud
     The device's connection merely TRANSITS the hotel network. The edge gateway
     is NOT in this path. This is commonly misread from the architecture diagram.

  PATH 2 — ACTUATION                cloud ──► (outbound tunnel) ──► edge ──LAN──► head-end
     The tunnel was opened OUTWARD by the edge. Nothing ever connects inward.

  PATH 3 — OFFLINE ONLY             device ──LAN──► edge ──► head-end
     The only time the device talks to the edge.
Current implementation gap

In this build the cloud creates its own adapter instance and talks to the head-end directly — Path 2 is not wired through the tunnel. The edge gateway exists, works and has passing tests, but is not in the actuation path.

Path 3 has the mirror gap: the appliance opens no listening socket, so a device has nothing to reach when the WAN drops. Both are Phase-2 work and both need planning now.

20. The simulator

You can build and test a complete adapter integration without any hotel hardware. The simulator models the behaviours that actually bite.

const adapter = new SimulatorAdapter({
  latencyMs: 120,           // base write latency, ±40% jitter
  failureRate: 0.05,        // 5% of calls fail as unreachable
  silentFailureRate: 0.02,  // acknowledged but NOT applied — the nastiest real bug
  driftRate: 0.01,          // state changes because a housekeeper used a wall switch
  binaryCurtainRooms: ['INN-0088'],   // exercise capability degradation
  seed: 42,                 // deterministic — evals must be reproducible
});
Build against the simulator first, deliberately

Access to real hotel hardware is the biggest velocity constraint on this project, and you cannot ask a hotel to unplug its head-end to test your error handling. Every failure path in your adapter should be exercised here before you touch a real system — especially silent failure and drift, which are the two you will otherwise discover in production.

21. Conformance testing

Every adapter ships a suite that runs at onboarding and nightly against a designated test room. This is the go-live gate for a property.

conformanceSuite(): ConformanceTest[] {
  return [
    check('lights on',        'lighting.on_off',     true, 'bedroom'),
    check('lights dim to 40', 'lighting.brightness', 40,   'bedroom'),
    check('setpoint 23',      'climate.setpoint',    23,   'bedroom'),
    check('mode cool',        'climate.mode',      'cool',  'bedroom'),
    check('curtains closed',  'curtains.position',    0,   'bedroom'),
    check('dnd on',           'dnd',               'dnd'),
  ];
}

22. Onboarding a property

Target: five working days for a 300-room property, once an adapter for its vendor exists.

DayStepDetail
1SurveyWhich vendor, which firmware, which integration surface. Room types and what each actually has. Network: is there an IoT VLAN?
1–2Room reference mappingHotel room number → vendorRoomId. Verify, don't assume. Import the ETS project for KNX; export the object map for INNCOM.
2ManifestsOne per room type — typically six to eight. Plus overrides for rooms with known faults.
2Property configTemperature band, quiet hours, spend caps, emergency number, languages, brand tone.
3Edge applianceInstall, bind to the property, verify the outbound tunnel, confirm it reaches the head-end.
3–4ConformanceRun the suite against a designated test room. Every capability in every room type.
4Device enrolmentProvision hubs, bind each to its room, verify the binding against the automation system.
5Content & go-liveMenu with spoken aliases, property FAQ, staff escalation targets, welfare protocol. Canary a floor before the property.
The step that goes wrong

Room reference mapping. It is tedious, it looks trivial, and getting it wrong means actions land in the wrong room while every log says they succeeded. Budget real time for verification, and re-verify after any refurbishment — a device moved between rooms produces exactly the same silent failure.
