How to use thisBefore you start

This document is a checklist to work through, not background reading. Follow the phases in order: each assumes the previous one passed, and a failure early makes later results meaningless.

Severity, and what it means for deployment

SeverityMeaningEffect on deployment
BlockerSafety, privacy, money, or the guest is told something untrueStop. No deployment to any room with a guest in it, regardless of schedule pressure.
MajorA core function does not work, or works unreliablyNo general rollout. A single staff-occupied test room is acceptable.
MinorWording, polish, an edge caseDeploy, log it, fix in the next release.
The one rule that overrides schedule

A device in a guest bedroom that says something untrue — claims an action succeeded when it did not, claims a capability it lacks, or implies it has summoned help it cannot summon — is worse than a device that does not work at all. A guest forgives a system that says “I can't do that”. They do not forgive one that lies, and neither will the hotel.

Every Blocker in Phase 2 exists for that reason.

Recording results

For each test record: date, tester, pass/fail, and for any failure the observed behaviour and a ticket reference. A test that was “probably fine” is a fail — re-run it until the result is unambiguous.

Phase 2Safety & adversarial

Zero tolerance

Every test in this phase is a Blocker. A single failure stops deployment — there is no threshold, no “mostly passing”, and no scheduling argument that outweighs it.

Before P2-19 can pass at a real property

The emergency number and crisis helpline in the property config must be correct for that country, and the hotel must have a documented welfare protocol naming who responds. Testing with the demo values proves the mechanism, not the deployment. Re-run these against the real property config before go-live.

Phase 4Resilience & degradation

Hotels lose internet. Vendors go down. Models rate-limit. What matters is not whether these happen but what the guest experiences when they do.

IDInduceExpectedSeverityResult
P4-01Set an invalid API key, restartFalls back to the deterministic path. Reply names what still works rather than reporting an error. Logs state the reason.Blocker
P4-02Block egress to the modelSame as above. No hang, no stack trace to the guest.Blocker
P4-03Model returns 503 (or wait for a real one)Retries with backoff, then degrades. Logs show the retry attempts and the final reason.Major
P4-04Force degradation level 2Simple requests still work; anything else offers the front desk.Blocker
P4-05Run the mock head-end with MOCK_FAILURE_RATE=1Guest told the room systems are unreachable. Never told the action succeeded.Blocker
P4-06MOCK_SILENT_FAILURE_RATE=1Verify-read catches it. Reply says “I've asked for that”, not “done”.Blocker
P4-07Repeated head-end failuresCircuit breaker opens. Other properties unaffected.Major
P4-08Kill the container mid-turnRestarts, healthy, no corrupt state. Confirmation tokens do not survive — a subsequent yes charges nothing.Blocker
P4-09Drop the WebSocket mid-conversationClient reconnects with jittered backoff. Context survives within 30 minutes.Major
P4-10Unknown deviceId404 / UNKNOWN_DEVICE, socket closed. No partial processing.Major
P4-06 is the one to run twice

Silent failure — the head-end acknowledges a write that never takes effect — is the most dangerous case in the whole system, because everything looks fine except the room. If the reply says “done” here, the verify-read is broken and every confirmation the system ever gives is untrustworthy.

P7-01 is the test people skip, and the one that hurts

Room reference mapping is tedious and looks trivial. Getting it wrong means actions land in the wrong guest's room while every log records success. Verify physically, room by room, and re-verify after any refurbishment — a device moved between rooms produces exactly the same silent failure.

Phase 10Go / no-go

Absolute gates

All must be true. Any single failure means no deployment to a room with a guest in it.

Zero open BlockersEvery one involves safety, privacy, money or truthfulness

Do not skip the staff-room stage

Staff will use the device in ways no test plan anticipates, and they will tell you plainly what is wrong. It is the cheapest feedback you will ever get, and it happens before a paying guest is exposed to it.

Phase 11Known gaps to close first

These are known to be incomplete today. Each must be closed or consciously accepted with a named owner before the corresponding stage.

GapBlocksDetail
Speech in and outTest roomService takes text. Wake word and recognition remain on the device; no server-side ASR or TTS.
Android clientTest roomNot yet migrated. Credential removal is the priority item.
Real vendor adaptersTest roomOnly the simulator exists. INNCOM/Interel need vendor documentation and hardware.
Edge appliance in the actuation pathPropertyBuilt and tested, but the cloud currently talks to the adapter directly. Required for LAN-only head-ends and WAN-outage behaviour.
Device LAN listenerPropertyAppliance is outbound-only, so a device has nothing to reach when the WAN drops. Offline mode cannot actuate until this exists.
Database persistenceCanaryAll state in memory; lost on restart. Schema exists, repositories do not.
Single instance onlyPropertyIn-memory state means no horizontal scaling and no redundancy. One reboot takes every room offline.
Staff / admin APICanaryNo HTTP surface and no authentication. Staff cannot see or manage requests.
PMS integrationPropertyStay data is seeded locally. No folio posting, no checkout event — so stay-scoped data has no deletion trigger.
MCP transport—Semantics implemented, protocol not. Existing MCP servers are not connected.
Fast-lane shadow evaluationCanaryFast-path rules are not continuously validated against the agent. Two regressed during development.
TLS / domainTest roomAndroid requires wss://. No device can connect without it.
Two of these are quietly the most dangerous

State is lost on restart. A container restart drops conversation context and pending confirmations. Harmless in testing; in a live property it means a guest mid-order is silently forgotten.

Single instance, no redundancy. One reboot takes every room in the hotel offline simultaneously. Acceptable for a canary floor with staff who know. Not acceptable for a property that has been told this is a product.
